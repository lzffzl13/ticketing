# 核心角色与用例

## 1. 文档目的

本文档描述 MVP 中各类参与者希望完成的事情，以及系统必须保证的结果。它用于连接业务需求、接口设计和测试，不在这里提前决定数据库表、框架或中间件方案。

当前状态：第一周已评审版本。涉及实现细节的参数仍需在对应模块开发前确认。

## 2. MVP 参与者

| 参与者 | 核心目标 | MVP 中不负责的事情 |
| --- | --- | --- |
| 消费者 | 找到场次、选择座位、完成购买，并管理自己的订单、电子票和候补请求 | 转赠、动态定价、真实第三方支付 |
| 运营人员 | 配置场馆和演出，创建可销售的场次及其座位快照 | 复杂营销、分销、多租户运营 |
| 核销人员 | 判断电子票能否入场，并查询核销尝试记录 | 离线核销、人工修改订单或票状态 |
| 支付模拟器 | 接收支付、查询和关单请求，并产生成功、失败、延迟、重复或乱序的结果与回调 | 接入真实支付渠道 |
| 系统定时任务 | 处理逾期锁座和待支付订单，并留下可检测、可恢复的处理结果 | 依赖无法追踪的一次性内存任务 |

## 3. 消费者用例

### C1. 浏览可售场次

**目标**：消费者能够找到当前允许售票的演出场次。

**前置条件**：运营人员已创建演出和场次，场次处于允许展示或销售的状态。

**主流程**：

1. 消费者查看演出和场次列表。
2. 系统展示场次时间、场馆、售卖状态和可用票档等必要信息。
3. 消费者选择一个场次进入座位选择流程。

**异常与边界**：已取消、未开放销售或已经结束的场次不能进入正常购票流程。

**验收要点**：场次是否可购买由明确状态判断，不能只依赖前端隐藏按钮。

### C2. 查看场次座位图

**目标**：消费者能够查看某一场次的座位布局、票档和当前可售状态。

**前置条件**：场次座位快照已经生成。

**主流程**：

1. 消费者打开场次座位图。
2. 系统返回区域、排、座号、坐标、票档和座位当前状态。
3. 消费者据此选择座位或请求系统推荐连座。

**异常与边界**：座位图展示的是查询时的状态，不承诺座位在后续提交时仍然可售。

**验收要点**：后续修改场馆座位模板，不得改变已经创建场次的座位图和票价快照。

### C3. 获取连座推荐

**目标**：消费者按人数和票档获得满足基础规则的连座候选。

**前置条件**：场次处于售卖中，且已经生成场次座位快照。

**主流程**：

1. 消费者提交人数、区域或票档等条件。
2. 系统寻找同区域、同排、同票档、座号连续且不跨过道的候选组合。
3. 系统按确定性规则排序并返回候选及推荐原因。
4. 消费者选择一个候选继续下单。

购买人数大于 1 时，“要求连座”默认开启，消费者可以主动关闭。开启后，所选座位必须位于同一区域、同一排、同一票档、座号连续且不跨过道。系统同时支持在座位图中手动选座；无论采用哪种方式，后端都以提交时的规则校验为准。

**异常与边界**：没有合适组合时返回“无可用候选”；推荐结果不是锁座结果，提交时必须重新校验。推荐算法不能推荐会制造新孤座的组合。

**验收要点**：相同输入和相同座位状态应得到可解释、可重复的结果。

### C4. 锁座并创建待支付订单

**目标**：消费者选择一组座位后，获得一个有支付期限的待支付订单。

**前置条件**：消费者身份有效，场次仍在售卖，所选座位在提交时均可售。

**主流程**：

1. 消费者提交座位组合和请求幂等标识。
2. 系统重新校验场次、票档、连座要求、孤座规则和全部座位状态。
3. 系统整体锁定全部座位，记录锁座期限。
4. 系统创建待支付订单和订单项，并保存座位与成交价格快照。
5. 系统返回订单号和支付截止时间。

**异常与边界**：任一座位已被占用时，整组锁座失败，不能创建包含部分座位的订单；重复提交同一请求不能创建多个有效订单。默认规则禁止本次选座制造新的孤座，但允许购买已经存在的孤座。孤座只在同一区域、同一排、同一票档且不跨过道的座位分段内判断；场次可以明确配置为允许制造孤座。

**验收要点**：并发购买相同或重叠座位时，最多一个请求成功，且不会出现部分锁定。

### C5. 模拟支付并获得电子票

**目标**：消费者为有效的待支付订单完成模拟支付，并取得每个订单项对应的电子票。

**前置条件**：当前时间早于订单支付截止时间，订单仍可支付，且尚未完成成功支付。

**主流程**：

1. 消费者在支付截止时间前对待支付订单发起模拟支付。
2. 支付模拟器受理支付请求，并可通过异步回调返回结果。
3. 系统通过回调或主动查单确认支付结果，并将结果应用到订单。
4. 支付成功时，系统把座位转为已售，并为每个订单项签发一张电子票。
5. 消费者查询订单和电子票。

**异常与边界**：支付截止时间只决定消费者能否发起新的支付，不等同于座位立即释放。截止时间后，即使座位仍因超时处理而保持锁定，消费者也不能发起新的支付；截止前已经受理的支付可以继续确认。订单到期时，系统必须先查单并尝试关闭未支付交易，只有确认交易未支付且关单成功后才能取消订单和释放座位。支付状态未知或支付服务不可用时暂不释放，并由重试和对账继续处理。失败、延迟、重复和乱序回调必须可复现，重复成功结果不能重复出票。

**验收要点**：一个订单项最多对应一张有效电子票，一个场次座位最多对应一张有效电子票。

### C6. 取消待支付订单

**目标**：消费者不再购买时，可以取消仍允许取消的待支付订单并释放座位。

**前置条件**：订单处于待支付状态，且没有已确认的成功支付。

**主流程**：

1. 消费者请求取消订单。
2. 系统以条件状态迁移取消订单。
3. 系统使对应锁座失效，并将仍由该订单占用的座位恢复为可售。

**异常与边界**：重复取消应返回一致结果；取消与支付回调并发时，不能同时得到“取消成功”和“支付出票成功”两种最终结果。

**验收要点**：已支付订单不能走待支付取消流程，释放操作不能误释放其他订单的座位。

### C7. 查询订单和电子票

**目标**：消费者能够查看自己的订单、支付结果、座位信息和电子票状态。

**前置条件**：消费者已登录或通过后续确定的演示身份机制访问自己的数据。

**主流程**：系统返回订单及其订单项、支付摘要和电子票摘要，并保持各类状态含义独立。

**异常与边界**：消费者不能查询其他人的订单和电子票；订单状态不能代替票状态，例如同一订单中的票未来可能分别处于有效、已核销或已退票状态。

**验收要点**：历史订单中的座位名称和成交价格来自订单快照，不随模板或当前票档改变。

### C8. 申请退票

**目标**：消费者对符合规则且尚未核销的电子票申请退款，退款完成后该票失效且座位可以回流。

**前置条件**：电子票属于当前消费者、状态为有效，且当前时间满足 `now < admission_open_at`。一个订单中的单张电子票可以独立申请退票。

**主流程**：

1. 消费者选择允许退票的票并提交申请。
2. 系统创建独立的退票记录，电子票进入退票处理状态并暂停核销资格。
3. 模拟退款成功回调到达后，系统才将退款视为成功。
4. 系统在同一个本地数据库事务中，将退票记录置为成功、使原电子票永久失效，并将对应场次座位恢复为可售。

**异常与边界**：到达 `admission_open_at` 的时刻开始拒绝新退票。开放前已经受理并进入退票处理状态的流程，在开放后继续等待明确的退款结果，不能擅自中断。重复申请不能创建多个有效退款；退票与核销并发时只能有一个成功；回流后再次售出必须签发全新的电子票。

**验收要点**：已核销票不能成功退票；旧票码在座位重新售出后仍然无效。

### C9. 登记和处理候补请求（条件增强）

**目标**：暂时没有合适座位时，消费者可以登记候补；座位回流后，系统按队列顺序自动分配并提供一次限时购买机会。

**前置条件**：场次仍允许候补，消费者提交场次、票档、人数和是否必须连座，不指定具体座位，也不在登记时付款。

**主流程**：

1. 消费者登记候补请求，系统按登记时间和稳定的请求标识确定先后顺序。
2. 座位因取消、超时或退票而回流时，系统优先尝试匹配等待中的候补请求。
3. 系统使用确定性的座位推荐规则，匹配票档、人数、连座要求和孤座规则。
4. 匹配成功后，系统原子锁定整组座位，创建待支付订单，并把候补请求置为已提供购买机会。
5. 消费者在可配置的候补支付期限内手动支付；支付成功后出票并完成候补。
6. 候补订单超时后释放座位，候补请求过期，系统继续尝试下一位符合条件的消费者。

**异常与边界**：候补采用自动分配而不是真正随机分配，相同队列和座位状态应得到可解释、可重复的结果。候补匹配与普通购买并发时不能重复锁定座位；存在可匹配候补时，回流座位应优先用于候补。首版不支持候补预付款、自动扣款、跨票档匹配或指定具体座位。

**交付门槛**：该用例不是最低交付线。只有核心购票、退票、核销闭环和可靠性测试按计划完成后才实施；若进度延期，优先删除本用例，不压缩核心测试时间。

## 4. 运营人员用例

### O1. 维护场馆座位模板

**目标**：运营人员配置场馆、区域和物理座位布局，供后续场次创建快照。

**主流程**：创建或修改场馆与区域，维护座位的排、号、坐标、过道边界和默认可用性。

**异常与边界**：模板修改只能影响之后创建的场次，不能反向修改已有场次座位和历史订单。

**验收要点**：修改或停用模板座位后，已有场次快照保持不变。

### O2. 创建演出、场次和票档快照

**目标**：运营人员基于一个场馆模板创建可独立销售和履约的场次。

**主流程**：

1. 创建演出基本信息。
2. 选择场馆和时间创建场次。
3. 为区域或座位配置本场次票档。
4. 配置售卖规则、是否禁止制造新孤座，以及允许核销的起止时间。
5. 系统从模板生成场次座位，并固化座位名称、位置、票档和价格快照。
6. 运营人员检查结果后开放销售。

**异常与边界**：快照生成失败时不能留下可售的半成品场次；同一场次不能重复生成两套有效座位。

**验收要点**：场次座位数量和映射完整，开放销售后使用的是场次快照而不是实时读取模板。

### O3. 管理场次售卖状态

**目标**：运营人员控制场次何时可展示、可购买或停止销售。

**异常与边界**：停止新销售不等于取消已有订单或使已出票门票失效；场次取消及批量退款不属于当前 MVP，除非后续明确加入并替代其他任务。

**验收要点**：售卖状态变化只阻止不允许的新操作，不破坏已经合法完成的交易。

## 5. 核销人员用例

### V1. 在线核销电子票

**目标**：核销人员扫描票码后，系统只允许有效电子票成功入场一次。

**前置条件**：核销人员具有演示用的工作人员身份，系统能够在线访问持久化数据。

**主流程**：

1. 核销人员提交扫描得到的票码。
2. 系统校验票码真实性、所属场次、允许入场时间窗口和电子票当前状态。
3. 系统以原子状态迁移将有效票变为已核销。
4. 系统记录本次成功尝试并返回结果。

**异常与边界**：核销设备或工作人员先选择当前场次。伪造、已退票、已核销、不属于当前场次、早于入场开放时间或不早于入场截止时间的票不能通过；多个入口同时扫描时最多一次成功。时间窗口采用 `admission_open_at <= 当前时间 < admission_close_at`，演示种子默认开场前 60 分钟开放、开场前 5 分钟截止，具体值允许按场次配置。

**验收要点**：每一次尝试都留下记录，包括失败和重复核销。

### V2. 查询核销记录

**目标**：核销人员能够按电子票、场次或时间查询核销尝试，解释一次扫描为何成功或失败。

**验收要点**：记录至少包含请求标识、电子票或票码摘要、场次、尝试时间、结果和失败原因；审计记录不能因重复请求被覆盖。

## 6. 系统触发用例

### S1. 处理锁座和订单超时

系统识别超过支付期限且仍为待支付的订单。若从未创建支付记录，说明没有发起外部支付，可以直接安全取消订单；若已有支付正在确认，系统必须先主动查单。已支付则进入统一的支付成功流程；未支付且关单成功后，才能以可重复执行的方式取消订单并释放仍属于该订单的锁座；状态未知时保持锁定并重试。任务重复运行不能误释放已支付或已被其他交易持有的座位，失败后必须可以检测和恢复。

### S2. 处理支付回调

系统验证支付回调的业务标识和当前状态，以幂等方式记录支付结果。异步回调和主动查单复用同一个支付结果处理入口；重复、延迟或乱序结果不能重复出票，也不能把已经确定的最终状态倒退到早期状态。支付模拟器还必须支持查单和关单，以复现支付成功与超时释放的竞争。

### S3. 检查数据一致性

系统检查订单、订单项、支付、电子票、场次座位和锁座记录之间是否违反关键不变量，并输出可追踪的差异。哪些差异允许自动修复、哪些只报警，将在实现该用例前决定。

### S4. 匹配候补请求（条件增强）

系统在座位回流后或通过可重复执行的扫描任务，按先到先得顺序匹配候补请求。匹配和整组锁座必须具备并发保护；任务重复执行不能为同一候补请求创建多个有效订单，也不能让同一座位同时进入普通订单和候补订单。

## 7. 当前不属于 MVP 的用例

- 真实第三方支付和真实资金结算。
- 候补预付款、自动扣款、跨票档候补、门票转赠、动态定价和复杂促销。
- 分销、多租户和反黄牛系统。
- 离线核销。
- 基于地理位置的附近热门场次。
- 场次取消后的批量退款和通知流程。

## 8. 已确认的业务决策

1. 同时支持手动自由选座和系统连座推荐；多人购票默认要求连座，但消费者可以关闭。
2. 支持订单内单张电子票独立退票；若第五周明显延期，可以按计划降级为整单退票。
3. 普通锁座和支付期限为 15 分钟。截止后不能发起新支付，即使座位因支付确认或超时清理尚未释放；截止前已受理的支付继续通过查单和关单确定最终结果。
4. 模拟退款成功回调到达后才视为退款成功；退票成功、电子票失效和座位回流在同一个本地数据库事务内完成。
5. 演示环境使用固定种子账号和简单登录令牌，至少区分消费者、运营人员和核销人员。接口同时校验角色和数据归属，不实现注册、找回密码、复杂 RBAC 和完整令牌生命周期。
6. 默认禁止一次选座制造新的孤座，推荐和最终锁座都执行该规则；已经存在的孤座允许购买，场次可以明确配置为允许制造孤座。
7. 核销必须匹配当前场次及其允许入场时间窗口，边界规则为 `open_at <= now < close_at`。
8. 候补采用“登记时不付款、匹配后锁座、消费者限时手动支付”；候补顺序先到先得，座位由确定性规则自动分配。
9. 退票申请在入场开放前截止，即 `now < admission_open_at`；此前已受理的退票在开放后继续处理。

## 9. 仍待详细设计的问题
