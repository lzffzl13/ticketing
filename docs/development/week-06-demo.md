# 第六周购票、退款重售与核销演示

`scripts/demo-checkins.ps1` 从固定规则厅种子和四个固定账号出发，通过本机真实 HTTP 完成两票购买、单票退款、回流重购、入场核销、失败审计和运营一致性报告。2026-10-18 已在 W6RUN1018 执行通过，原命名空间重跑和真实重启后验证通过，具体证据见[第六周周报](../progress/week-06.md)。学习讲解与负责人验收单独进行。

## 1. 启动与运行

先按[本地环境](local-environment.md)启动开发 MySQL，配置原有票码密钥并启动包含 V6 核销迁移的应用。默认开发库端口 3307，默认应用地址 `http://127.0.0.1:8080`；测试库与测试 profile 不参与本演示。脚本仅接受 localhost / 127.0.0.1 的 HTTP 地址，密码从 `.env` 读取，登录令牌不写入状态文件或日志。

```powershell
.\scripts\demo-checkins.ps1 -Namespace W6A
```

应用使用其他端口时传入 `-BaseUrl http://127.0.0.1:18090`。一套命名空间始终使用相同地址；脚本发现地址或原数据不匹配时停止，并保留历史。

脚本先复用 `seed-week2.ps1` 创建 56 座的独立规则厅与不可变 DRAFT 快照，再创建独立的 `SESSION-CHECKIN-W6A` 交易场次。种子准备好后才读取一次系统 UTC 时间，设置开场为基准后 62 分钟、入场开放为基准后 2 分钟、截止为基准后 57 分钟。正常 HTTP 请求可在开放前完成购票、退款与重售，随后脚本以每次最多 15 秒的真实等待跨过开放边界。每次等待都会输出剩余时间。

原支付期限仍为 15 分钟，不修改应用 Clock，不刷新已开售场次时间，不通过 SQL 写入订单、票、退款、座位或核销状态。默认最多等待 180 秒；`-MaxAdmissionWaitSeconds 0` 可以在购退款重售完成后立即返回阶段信息，稍后续跑。

## 2. 主流程与断言

1. `consumer1` 查询两座连座推荐，验证推荐没有修改库存，再以保存的请求键下单、模拟支付并投递原成功通知，签发两张原票。
2. 保存两张原票的票号、身份与凭证，仅对其中一张申请全额退款。成功通知经普通入口处理后，原票变为 `REFUNDED`，另一张仍可入场；原订单项成交价和原成功收款保留。
3. `consumer2` 以普通手选、支付入口购买回流的同一场次座位，获得不同票号的新票。再次投递旧退款成功通知，确认新占用仍为 `SOLD`。
4. 等待真实入场开放后，`checker1` 核销新票和原订单保留票。每张仅一条 `SUCCESS`，票变为 `CHECKED_IN`；最后一张未退款票核销后，两个订单均归集 `COMPLETED`，两个座位仍为 `SOLD`。
5. 再扫新票得到 `ALREADY_CHECKED_IN`，扫退款前保存的旧码得到 `REFUNDED`。查询持久核销审计，验证首次成功、重复拒绝、旧码拒绝分别有记录，旧票没有成功记录。
6. 运营查询 `GET /api/operations/sessions/{id}/consistency`，要求 `consistent=true`、`differences=[]`、三张历史票、一张退款、两条成功核销及零未决/人工恢复任务。

本演示中核销人员使用 `POST /api/checkins`，请求体为 `sessionId` 与 `credential`。审计查询使用 `GET /api/checkins?sessionId=...&ticketId=...&afterId=...&limit=100`，按 `nextAfterId` 逐页读取；核销接口为每次扫描保存独立记录，脚本不会把旧成功响应当成再次放行。

## 3. 分阶段与中断续跑

```powershell
# 完成购退款及重售，不等待也不核销。
.\scripts\demo-checkins.ps1 -Namespace W6B -PrepareOnly

# 原窗口开放后续跑；重复订单、支付和退款请求复用原身份。
.\scripts\demo-checkins.ps1 -Namespace W6B

# 全程完成后只读检查，窗口截止后也可执行。
.\scripts\demo-checkins.ps1 -Namespace W6B -VerifyOnly
```

状态位于被 Git 忽略的 `.local/demo-checkins/<Namespace>.json`。创建场次、下单和申请退款前先保存原意图，响应丢失后以原编号重放；已提交核销由持久审计确认，避免把本机文件当成入场成功事实。成功演示重跑默认进入只读验证，不追加扫描、不创建新订单、不删除原记录。

如果中断发生在退款受理前，并且恢复时已超过原入场开放时间，业务应拒绝新退款。若中断后超过支付或入场期限，也不能通过改时间或清历史修补；保留原命名空间及证据，使用新的 W6 命名空间重新演示。已受理退款仍可按原协议完成，已出票的新订单也不要求在开放前完成支付；具体能否续跑以接口实际状态为准。

状态文件包含退款前旧码、新码和保留票码，属于敏感本机资料。不要把整份状态文件打印到终端或纳入 Git。脚本只输出订单、票和退款的数字身份、阶段和窗口，不输出票码、密码或 Bearer 令牌。中断后复用相同数据库与票码密钥配置；紧急撤销旧密钥后，旧凭证会按验真规则拒绝，不能把该场景称为本演示的 `REFUNDED` 旧码验证。

## 4. 报告与失败处理

安全的一致性报告单独保存为 `.local/demo-checkins/<Namespace>-consistency.json`。报告是一次本地一致快照，检测器不直接修业务数据；发现差异时脚本保留报告并失败。先核对报告中的规则、对象与观察值，再依据既有支付/退款恢复协议处理未决事实，矛盾或人工标记交由运营核查。不能根据期望演示结果直接改表。

真实演示证明正常 HTTP 生命周期、历史退款回流、唯一成功审计和报告无差异；时间四边界、入口并发、事务写失败及故障夹具检测由独立自动化测试验证，不能用本脚本替代这些测试。已核销失败的未提交事务不能放行；返回系统错误时应查看原票审计，确认持久成功记录后再决定后续处理。
