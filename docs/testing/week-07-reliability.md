## 参数、流程与检查点

`Week7InventoryReliabilityIT` 是一项 JUnit 测试，内部运行两种负载各十轮，每轮新建一个 24 座场次。布局为三排，每排一个八座分段，单区域、单票档、每座 100 元，禁止制造新孤座。八个消费者使用十二个工作线程，每段四个请求，一起到达 latch 后统一放行；每轮轮换/反转提交顺序，交替反转提交座位编号顺序，调度赢家不预设。

- ANCHOR_PREFIX：每段分别买 `[1..2]`、`[1..4]`、`[1..6]`、`[1..8]`，全部共享锚点，每段必须恰一胜者。
- OVERLAP_CHAIN：每段分别买 `[1..4]`、`[3..6]`、`[5..8]`、`[1..8]`，允许无交集的首尾两组都成功；每段必须一至两胜者，每个败者必须确实与最终赢家相交。

调用入口为真实 `OrderService.create`。成功后检查原期限、价格快照、订单项/锁明细/当前持有座位集合完全相同；失败请求无订单，胜者没有共享座位，未被购买座位保持 AVAILABLE，ACTIVE 历史锁不重复。每轮读取同场次一致性报告，订单数与胜者数一致，全部为正常待支付。这个实验只验证支付前库存分配，不把“此时没有电子票”解释为支付出票超卖验证。

`Week7PaymentReliabilityIT` 是三项独立 JUnit 测试，复用既有真实数据库故障夹具：

| 场景 | 注入位置与主流程 | 必须成立的结果 |
| --- | --- | --- |
| 本地提交后通知确认失败 | 本地出票成功后、模拟器 acknowledge 前抛异常；并发重投成功通知、晚到 PROCESSING、重复扫描 | 原两张票 ID 不变，订单 PAID，首次确认时间不被重写，不增加恢复失败次数 |
| 旧任务过期接管与真实出票回滚 | 旧任务取得真实 PROCESSING 快照后暂停；测试 Clock 超过 60 秒租约，新任务读到渠道成功；先放行旧任务，再让新任务在真实首票 INSERT 后异常；到持久退避时间后两个 scanner 同时选中原单 | 旧 token 不能清新领取；失败后全组 HELD、票零张，过期领取与写失败各计一次，按第二次失败退避 15 秒；两个重试只增加一次渠道查询并签发原两张票，随后旧/重复通知不倒退 |
| 取消重售后的历史通知 | 原 FAILED 订单到期安全取消，consumer2 通过正常下单/支付购买相同两座；旧 FAILED/PROCESSING 通知与旧单恢复任务并发重放 | 原单 CANCELLED/EXPIRED，新单 PAID/CONSUMED，原单零票，新票身份与 SOLD 占用不变 |

入口编排不跨一整个数据库事务：渠道事实独立提交，本地成功/取消沿既有短事务，扫描的批次无外层写事务。异常均在测试 spy 中注入，不给生产增加故障 API。每个阶段保存预期/实际与公开业务状态，实际失败会令测试失败，最终再次检查一致性。

## 判定依据

重叠请求的正常失败是明确业务冲突，不是测试失败。测试同时检查：胜者整组占座；败者没有订单或部分锁；当前占用与订单、锁和明细一一对应；支付恢复不重复出票、不倒退终态；旧任务不能清除新任务的领取身份。最后调用既有 `ConsistencyService.inspect` 复查本地跨表关系。

`consistent=true` 仅表示报告所覆盖的本地规则没有矛盾；每个场景仍须单独检查期望业务终态与渠道通知确认，不能只靠空差异报告宣称支付已全部完成。

## 证据限制

这是服务层正确性实验，没有 HTTP 发压、固定外部 RPS 或生产容量结论。工作线程数不等于同时运行的数据库事务数，Hikari 最大连接数为 5，实际参数由实验记录。

上述自动化测试通过 latch 暂停旧任务、控制 Clock 超过租约，并在真实 SQL 后或通知确认阶段抛出异常。它验证特定故障窗口和恢复行为，不是实际操作系统杀进程、数据库宕机或跨机网络丢包。第四至六周真实重启属于历史证据；第七周在后续独立实例中实际完成的强制终止、原编号续跑恢复与只读重跑另见[真实重启导读](../development/week-07-restart-demo.md)，与这些进程内故障分开记录。
