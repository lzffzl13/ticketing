# 业务不变量与测试场景

## 1. 文档目的

本文档把已经确认的业务不变量转换为可以自动化执行的 Given/When/Then 场景。它回答“系统必须证明什么”，不提前决定 JUnit、Testcontainers 或压测工具的具体写法。

当前状态：第一周已评审版本。测试数据均由后续固定种子程序生成，不代表真实客户、生产流量或性能结论。

SCN-04/05/06 的真实下单、争抢、整组回滚和旧候选拒绝已实现并执行；SCN-07/08 也用于最终购买验证。场次锁、管理竞争、幂等和截止边界见 W4-A01 至 A12。第四周支付/出票/取消及第五周自动扫描已经实现并执行，证据见[第四周周报](../progress/week-04.md)和[第五周周报](../progress/week-05.md)。SCN-27 新增扫描器、活动领取和旧持有者的数据库回归。第五周 RefundIT / RefundRecoveryIT / RefundSimulatorIT 落地 SCN-17/18/19A/20/21/22。第六周 CheckinIT 已补正式 SCN-19 / 23 / 24 / 25、旧码回售及审计原子回滚；ConsistencyIT 补本地差异检测及同快照竞争，实际执行证据见[第六周周报](../progress/week-06.md)。条件候补仍未实现。

## 2. 测试层级约定

| 层级 | 主要证明内容 | 示例 |
| --- | --- | --- |
| 领域单元测试 | 不访问数据库的纯业务规则和状态迁移 | 连座、孤座、允许的状态迁移 |
| 数据库集成测试 | 约束、事务原子性、条件更新和快照隔离 | 整组锁座回滚、重复出票防护 |
| 并发集成测试 | 多事务竞争时仍保持不变量 | 重叠锁座、支付与超时、双入口核销 |
| 端到端测试 | 从接口入口到持久化结果的完整流程 | 选座下单、支付出票、退票回流、核销 |
| 故障恢复测试 | 外部交互失败或进程中断后能够检测和恢复 | 支付成功但本地提交失败、任务重复执行 |

同一条不变量可能需要多个层级共同证明。单元测试证明规则计算正确，不代表数据库并发时也一定正确。

## 3. 固定场景数据

固定数据分为小型规则测试厅、中型主演示场馆和参数化规模数据，详细定义见 `docs/data/seed-data-design.md`。测试不得依赖无法复现的随机座位布局：

- 消费者 `consumer1`、`consumer2`，运营人员 `operator1`，核销人员 `checker1`。
- 规则测试厅包含两个区域、五排、56 个座位和两个票档。
- 主演示场馆包含两个区域、14 排、246 个座位和三个票档。
- 一个未开售场次、一个正在售卖场次和一个处于核销窗口的场次。
- 两个场馆都包含过道分段和默认不可售座位。
- 至少一组可以形成新孤座和一组已经存在孤座的布局。
- 支付模拟器能够返回成功、失败、延迟、重复、乱序、查单失败和关单竞争。

所有涉及时间的测试使用可控制的测试时钟，不真实等待 15 分钟。并发测试必须记录线程数、起跑方式和最终数据库断言；性能测试另行定义环境和指标，不能从功能并发测试推导吞吐结论。

## 4. 不变量总表

| 编号 | 不变量 | 最低验证层级 |
| --- | --- | --- |
| INV-01 | 模板修改不能污染已经创建的场次座位和历史订单快照 | 数据库集成 |
| INV-02 | 同一场次座位同一时刻最多存在一个有效锁定 | 并发集成 |
| INV-03 | 一组座位必须整体锁定或整体失败 | 数据库集成、并发集成 |

| INV-06 | 一个订单同一时刻最多一笔进行中支付，最多一笔成功支付 | 数据库集成、并发集成 |

| INV-19 | 只有入场开放前才能发起新退票，已受理流程不因开放时间到达而中断 | 领域单元、数据库集成 |

## 5. 模板与场次快照

### SCN-01 修改模板不影响场次快照

**覆盖**：INV-01

```text
Given 已根据场馆模板创建场次座位，并记录区域、排号、座号、坐标和票档价格
When  运营人员修改模板座位名称、坐标和默认区域
Then  已有场次座位保持创建时的全部快照值
And   之后新建的场次使用修改后的模板值
```

### SCN-02 修改票档不影响订单成交快照

**覆盖**：INV-01、INV-16

```text
Given 消费者已经按 380 元创建订单项
When  运营人员修改尚允许修改的场次票档显示信息
Then  历史订单项仍显示 380 元及下单时的座位信息
And   订单金额不被重新计算
```

### SCN-03 不可售座位重新启用的前置校验

```text
Given 一个未开售场次中存在没有票档的 UNAVAILABLE 座位
When  运营人员尝试将其改为 AVAILABLE
Then  系统拒绝缺少票档或价格的启用请求
When  运营人员补齐票档和价格后再次启用
Then  座位成功变为 AVAILABLE
```

## 6. 推荐、孤座与整组锁定

### SCN-04 重叠座位并发锁定

**覆盖**：INV-02、INV-03

```text
Given A1-A3 均为 AVAILABLE
When  consumer1 同时请求 A1-A2，consumer2 请求 A2-A3
Then  两个请求最多一个成功
And   失败请求不会保留任何有效锁座或待支付订单
And   A2 只属于成功请求的一组锁座
```

并发测试使用屏障让事务尽量同时开始，循环执行多轮并在每轮后查询数据库不变量，而不只断言接口返回值。

### SCN-05 整组锁定中途失败必须回滚

**覆盖**：INV-03

```text
Given A1、A2 可售，A3 已被其他订单锁定
When  消费者请求整体锁定 A1-A3
Then  请求失败
And   A1、A2 仍为 AVAILABLE
And   不创建有效座位锁、订单或订单项
```

### SCN-06 推荐后候选被抢占

**覆盖**：INV-04

```text
Given 系统向 consumer1 推荐 A1-A3
And   consumer2 在 consumer1 提交前成功锁定 A2
When  consumer1 提交原推荐组合
Then  系统重新校验并拒绝整组锁座
And   A1、A3 不被 consumer1 部分锁定
```

### SCN-07 连座边界

**覆盖**：INV-05

跨区域、跨排、跨票档、座号不连续或跨过道的组合不能被系统作为连座推荐。手动选座自动不强制连座，无需关闭开关，但仍必须满足可售状态和场次孤座规则；不可售或已占用座位在两种方式下都不能购买。规则见 [ADR-0008](../decisions/0008-manual-seat-selection.md)。

```text
Given 同一排 1-6 号在过道左侧、7-10 号在右侧，全部可售
When  消费者手动选择 5、6、7 号
Then  纯选座规则允许该组合，剩余 1-4 和 8-10 均未形成新孤座
And   同一组合在要求连座的校验中被拒绝，不能作为连座推荐
```

右侧仅有 7-8 号时，手选 5、6、7 会留下新孤座 8，应拒绝；所选 6 号已锁定时，手选同样拒绝。纯规则证据见第三周；第四周另有最终购买规则与原子锁座测试，两类证据分别记录。

### SCN-08 禁止制造新孤座

**覆盖**：INV-05

```text
Given 同一座位分段中 1-4 号连续可售
When  消费者选择 2-4 号，留下单独的 1 号
Then  推荐不返回该组合，手动锁座也拒绝该组合
```

另需验证：购买原本已经存在的孤座允许；排首排尾正确判断；过道、不可售位和票档边界切断分段；场次关闭孤座限制后允许原组合。

## 7. 订单与支付

### SCN-09 支付失败后截止前重试

**覆盖**：INV-06

```text
Given 订单为 PENDING_PAYMENT，第一笔支付已经明确 FAILED，且尚未到截止时间
When  消费者再次发起支付
Then  创建新的支付记录
And   第一笔失败记录保留不变
And   同一时刻只有第二笔支付处于进行中
```

### SCN-10 并发发起两笔支付

**覆盖**：INV-06

```text
Given 订单可支付且当前没有进行中支付
When  两个请求同时发起支付
Then  最多一条支付记录进入 INITIATED 或 PROCESSING
And   重复幂等请求返回原支付结果
And   相同幂等键但请求内容不同必须被拒绝
```

### SCN-11 截止后座位未释放也不能新支付

**覆盖**：INV-07

```text
Given 订单已超过 payment_expires_at，但超时任务尚未处理，座位和锁仍为 HELD/ACTIVE
When  消费者发起一笔新支付
Then  系统因超过支付截止时间拒绝
And   不以“座位仍锁定”为理由接受支付
```

### SCN-12 截止前支付、截止后回调成功

**覆盖**：INV-07、INV-08、INV-09

```text
Given 支付在截止前已经被模拟器受理
And   到期任务查单时结果暂时未知
When  成功回调在截止后到达
Then  系统确认支付、消费锁座并签发电子票
And   到期任务不能释放这些座位
```

### SCN-13 关单与支付成功竞争

**覆盖**：INV-07、INV-08

模拟器先确认支付成功时，关单失败且本地出票；模拟器先关单成功时，迟到结果不能再改为成功，本地取消订单并释放座位。任何一次执行都不能同时出现成功支付和已释放座位。

### SCN-14 重复和乱序支付结果

**覆盖**：INV-08

对同一个支付编号重复投递成功、先成功后失败、先查单成功后再收到成功回调。最终只能有一笔成功支付、每个订单项一张电子票，支付和订单终态不倒退。

### SCN-15 支付成功事务中断

**覆盖**：INV-09、INV-17

在更新支付后、更新订单后、更新部分座位后和签发部分电子票后分别注入异常。每次本地事务必须全部回滚；重新处理相同成功结果后，一次性完成支付、订单、整组座位、锁和全部电子票的变化。

### SCN-16 主动取消与进行中支付

```text
Given 订单存在 PROCESSING 支付
When  消费者请求取消订单
Then  系统不能直接取消并释放座位
And   必须先查单并安全关单，或者返回“支付确认中”并由后续任务处理
```

## 8. 退票与座位回流

### SCN-17 单票退票不影响同订单其他票

**覆盖**：INV-10、INV-16

```text
Given 一个 PAID 订单包含三张 VALID 电子票
When  中间一张票退款成功
Then  该票变为 REFUNDED、对应座位变为 AVAILABLE
And   其余两张票仍为 VALID、对应座位仍为 SOLD
And   订单汇总状态为 PARTIALLY_REFUNDED
```

### SCN-18 重复申请和重复退款结果

**覆盖**：INV-10、INV-17

同一张票并发申请两次退票，最多创建一笔有效退票流程；同一成功结果重复到达，只产生一次退款成功、一次座位回流，订单退款金额不重复累计。

### SCN-19 退票申请与核销竞争

**覆盖**：INV-11

```text
Given 电子票为 VALID
When  退票申请和核销请求并发执行
Then  最多一个操作取得 VALID 状态的迁移权
And   最终不能同时存在 SUCCEEDED 退票和 SUCCESS 核销
And   所有核销尝试仍保留审计记录
```

实际测试遵守互斥时间窗口：场次锁持有时让新退票等待，再把测试 Clock 从 open-1µs 推到 open，与正式核销竞争；新申请因锁后截止被拒、核销可成功。另覆盖开放前已受理退款的成功/失败通知与正式扫描竞争。不能把同一 now 两种新请求均可受理当作真实业务前提。

### SCN-19A 退票申请时间边界

**覆盖**：INV-19

| 当前时间与动作 | 预期结果 |
| --- | --- |
| `admission_open_at - 1ms` 发起退票 | 受理，票进入 `REFUNDING` |
| `admission_open_at` 发起退票 | 拒绝，票保持 `VALID` |
| `admission_open_at + 1ms` 发起退票 | 拒绝，票保持 `VALID` |
| 开放前已进入 `REFUNDING`，开放后收到退款成功 | 继续处理为 `REFUNDED` 并回流座位 |
| 开放前已进入 `REFUNDING`，开放后收到退款失败 | 继续处理为 `FAILED`，票恢复 `VALID`，但因已开放不能再次申请退票 |

### SCN-20 退款成功事务中断

**覆盖**：INV-12

分别在退票单成功、票失效、座位回流和订单汇总更新之间注入异常。事务失败后不能观察到“票仍有效但座位已回流”或“票已失效但座位未回流”；重试相同结果后一次性完成全部变化。

### SCN-21 退款失败恢复票

```text
Given 电子票为 REFUNDING，退票单为 PROCESSING
When  模拟退款明确失败
Then  退票单变为 FAILED，电子票恢复 VALID
And   座位仍为 SOLD
And   消费者可以重新申请退票或在有效窗口内核销
```

### SCN-22 回流后重新售出

**覆盖**：INV-13

```text
Given 旧票退款成功，原座位已经回流
When  新消费者购买同一场次座位并支付成功
Then  系统创建新的订单项和新电子票
And   旧票保持 REFUNDED
And   扫描旧票返回 REFUNDED，不能核销新票对应的座位
```

## 9. 核销与审计

### SCN-23 双入口并发核销

**覆盖**：INV-14

```text
Given 一张符合场次和时间窗口的 VALID 电子票
When  两个核销入口同时扫描
Then  仅一个请求将票改为 CHECKED_IN 并记录 SUCCESS
And   另一个请求记录 ALREADY_CHECKED_IN
And   两条核销尝试均可查询
```

### SCN-24 无效票码也留痕

**覆盖**：INV-14

提交签名错误或无法关联电子票的票码，系统拒绝核销并追加 `INVALID_CREDENTIAL` 记录。记录可以没有电子票标识，但必须包含当前场次、时间、核销人员、请求标识和凭证安全摘要，不能保存原始敏感票码。

### SCN-25 核销时间边界

**覆盖**：INV-15

| 当前时间 | 预期结果 |
| --- | --- |
| `open_at - 1ms` | `TOO_EARLY` |
| `open_at` | 允许核销 |
| `close_at - 1ms` | 允许核销 |
| `close_at` | `TOO_LATE` |

另需验证属于其他场次的有效票返回 `WRONG_SESSION`，且这些失败不会改变电子票状态。

## 10. 状态隔离与重复任务

### SCN-26 状态不能互相替代

**覆盖**：INV-16

至少验证以下合法组合能够被正确表达：

- 订单 `PENDING_PAYMENT`、支付 `PROCESSING`、座位 `HELD`、尚无电子票。
- 订单 `PAID`、支付 `SUCCEEDED`、座位 `SOLD`、电子票 `VALID`。
- 订单 `PARTIALLY_REFUNDED`，同一订单内同时存在 `REFUNDED`、`VALID` 和 `CHECKED_IN` 电子票。
- 订单 `COMPLETED`、座位仍为 `SOLD`、电子票为 `CHECKED_IN` 或因时间窗口结束而不再允许入场。

### SCN-27 超时任务重复执行

**覆盖**：INV-17

对同一个到期订单并发或连续执行多次超时任务。最多一次完成安全取消和座位释放；后续执行不新增支付、订单、锁座或释放记录，也不能释放已被新订单持有的座位。

## 11. 候补测试（条件增强）

### SCN-28 候补先到先得且确定性分配

```text
Given 两个条件相同的 WAITING 候补请求按先后顺序登记
And   仅回流一组满足条件的座位
When  候补匹配任务运行
Then  先登记的请求进入 OFFERED
And   后登记的请求保持 WAITING
And   相同数据下自动分配结果可重复解释
```

### SCN-29 候补匹配任务重复执行

**覆盖**：INV-18

同一请求被两个匹配任务同时处理，最多创建一个 `OFFERED` 结果、一张待支付订单和一组有效锁座。

### SCN-30 候补与普通购买竞争回流座位

**覆盖**：INV-18

回流座位存在可匹配候补时，候补匹配和普通购买并发执行。最多一方成功锁座；若实现已经取得候补优先处理权，普通购买不能绕过该权利。失败一方不能留下部分锁座或订单。

### SCN-31 候补机会超时不自动回队尾

候补订单安全超时后，请求从 `OFFERED` 进入 `EXPIRED`，释放座位并继续匹配下一位；原请求不会恢复 `WAITING`，消费者如需继续候补必须重新登记。

## 12. 故障恢复检查点

以下步骤需要在实现后提供可重复的异常注入点：

1. 支付模拟器已经成功，但本地尚未处理回调时终止应用。
2. 本地收到支付成功，在事务提交前注入异常。
3. 到期任务查单成功后、关单前终止应用。
4. 模拟器关单成功后、本地取消事务提交前终止应用。
5. 模拟退款成功后、本地退票事务提交前终止应用。
6. 候补匹配选出座位后、锁座事务提交前终止应用。

恢复后通过回调重投、定时重试或对账任务继续处理。每个实验要断言最终不变量，而不只观察日志中出现异常。

## 13. 完成标准

- 每条关键状态迁移至少映射到一个自动化测试场景。
- 锁座、支付回调、超时释放、退票和核销均包含重复或并发路径。
- 所有时间边界使用可控时钟，所有并发场景检查最终数据库不变量。
- 候补只有在功能进入本版本时才实现对应测试，但不能只实现候补正常路径。
- 后续测试代码使用场景编号命名或注释，便于从测试追溯到业务规则。

## 14. 第六周一致性故障样例

[实际差异报告](examples/week6-consistency-difference.json) 来自 2026-10-18 执行的 `ConsistencyIT` ORDER_TOTAL 参数。测试在隔离库中走真实两票购票/支付出票，再明确注入 `total_amount + 1`，保留原订单项和支付金额，故报告发现 C01_ORDER_STRUCTURE 与 C04_PAYMENT_BINDING。测试断言检测前后全部本地及渠道表不变，不能把它称为真实生产异常或自动修复证明。

报告 checkedAt 使用受控测试 Clock 的 2026-10-10 时间；对象编号来自隔离测试库自增，本轮样例执行后后续测试会清理该夹具。重做时编号可能不同。执行 `scripts/test.ps1 -Integration` 会再次生成 `target/week6-consistency-difference.json`，无需在开发库破坏业务事实。

处理该例应先保留报告并核对原订单项/支付凭证，定位订单金额被错误改动的原因；不能把支付金额改成错误订单金额，不能重复扣款、补票或释放座位。修复缺陷并经过人工核查后，再通过受控数据修复或既有业务恢复协议处理，重新检测。系统没有开放任意修改资金/库存的 HTTP 接口。
