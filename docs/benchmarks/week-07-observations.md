## 持久恢复积压实验

入口为 `scripts/benchmark-payment-recovery.ps1`，显式选择 `PaymentRecoveryBacklogExperiment`；普通 Test / IT 发现不选择这个名称，还必须启用专用系统属性。运行前核对库名 `ticketing_test`，不清历史。复现：

```powershell
.\scripts\start-infra.ps1 -IncludeTest
.\scripts\benchmark-payment-recovery.ps1
```

默认六个正式档位：两种工作负载各五十个独立两座订单，批量上限 1 / 10 / 50。NO_PAYMENT_TIMEOUT 从未发起支付，扫描后安全取消/释放；CHANNEL_SUCCESS 在截止前受理并保存独立渠道成功，故意不本地应用或投通知，到期扫描后补齐出票。每种工作负载另有五单预热，共三百个正式订单、十个预热订单。新场次各一百座，单区域/票档、每座一百元、每排二十座、禁止新孤座，确定性的相邻两座对，无随机数据。

使用明确标注的 **2000-01-01 合成业务 Clock** 创建订单，保留原九百秒期限，再推进到原截止，使整组积压同时符合候选条件。它不会真实等待十五分钟。由于生产 scanner 扫描全库，每档准备及放行前按生产候选谓词核查本档以外候选必须为零，发现外部待处理即停止保留证据；年代只隔离现代历史，不改变 scanner 或旧业务数据。

一个工作线程紧凑调用真实 `scanOnce`，逐笔按对应分支沿用场次/订单锁与完整恢复事务。无支付分支直接安全取消，渠道成功分支查到成功后出票；这两个负载都不调用渠道 close，未测仍在 PROCESSING 交易的关单开销。无外部 HTTP 流量，无故障负载，无新增订单到达。候选数和实际完成数分开记录，默认每批必须相同、积压持续减少；完成后检查每单原期限/明细/锁、全部库存和票，以及一致性报告，再重复空扫描确认终态不变。环境与上一节相同，实验与其他项目负载生成器串行。

### 指标定义

- `total_scan_ns`：真实 `System.nanoTime` 包围各 `scanOnce` 后求和，包含候选查询、逐单完整恢复与提交，不含造数、结果查询、断言、报告或输出。
- `drain_ns_including_observation_gaps`：开始计时扫描到最后一次扫描返回的真实时间，包含前面各批之间的结果观测 SQL。文中的统一放行指这一计时起点；此前 Clock 推进、资格预检与初始报告属于准备阶段，不计入该值或完成上界。
- `completion_upper_bound_ns`：每单首次观察到终态的批次返回时刻减统一放行时刻，是完成上界；批内早完成的订单也记到整批返回，不能当作精确提交时刻。批量五十的所有订单同一个上界，不能由此认定其真实单笔中位耗时都更高。
- `completed_orders_per_scan_second`：完成订单数除以扫描累计时长，不含观测间隙。这里没有生产默认每轮结束后的一秒等待，不能推导默认调度下的自动释放时延、生产吞吐或 SLA。

两种工作负载分别先预热，正式批量顺序为 1/10/50 与 50/10/1；只有每档一次有限观测，预热不能控制全部 JVM、缓存和系统噪声。
