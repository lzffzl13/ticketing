## 2. 核销与审计建议

业务问题：两个入口扫描同一张票，只能放行一次；失败、重复和伪造票码也必须可以追溯。

备选一是客户端请求键去重并重放原成功响应，另存每次运输尝试；备选二是每个有效核销 POST 都追加一次独立尝试，首次 SUCCESS，之后 ALREADY_CHECKED_IN。建议选择第二种：副作用幂等且每次扫描都有明确结果，避免重试的旧 SUCCESS 被误解成第二次放行。响应丢失后可按票/场次/时间查询原成功记录；服务不可用或事务未提交时不得放行。

建议新增 V6 `checkin_record` 一表：id、服务端 request_id、checker_id、所选 session_id、可空 ticket_id、SHA-256 凭证摘要、attempted_at、result。只保存摘要，不保存原始票码、Bearer 或签名密钥。结果包括 SUCCESS、ALREADY_CHECKED_IN、REFUNDING、REFUNDED、INVALID_CREDENTIAL、WRONG_SESSION、TOO_EARLY、TOO_LATE、SESSION_NOT_FOUND、INCONSISTENT_STATE。为场次/时间、票/时间建索引；用生成列唯一约束保证每票最多一条 SUCCESS，外键绑定工作人员、场次（不存在时可空）及票。不存在场次另保留 submitted_session_id 以便追溯原输入。

核销入口 `POST /api/checkins` 只允许 CHECKER；JSON 提交 sessionId、credential。核销业务拒绝返回带明确 result 的正常业务响应，避免抛异常把失败记录回滚。格式错误、未登录、越权请求在 HTTP/安全层拒绝，不算受理的扫描，审计范围须明确写入接口文档。

查询 `GET /api/checkins` 允许 CHECKER / OPERATOR，以 sessionId、ticketId、from、to 过滤，使用 id 游标和最大 100 条分页，返回安全字段与结果。不新增场馆级角色分配模型。

成功路径复用场次写锁，之后按既有方向锁订单、座位、票，锁内取当前时间并重验票状态、订单已付款与座位 SOLD。`VALID -> CHECKED_IN` 和 SUCCESS 审计同一 READ_COMMITTED 本地事务提交；任何写入失败整体回滚并返回系统错误。失败业务结果同事务追加审计、不改变票。未知/伪造票码不根据未验真的票号访问或锁定原票。

落实已有订单规则的一部分：最后一张未退款票核销且其余票均 CHECKED_IN / REFUNDED、无进行中退款时，同事务归集 COMPLETED；全退保留 FULLY_REFUNDED。入场截止后的无人到场订单批量归集暂不在本闭环新增，作为已知限制记录，不将其报告为库存/资金异常。

## 3. 一致性检查建议（Q-08）

业务问题：数据库跨表事实可能因缺陷或人工改动发生矛盾，但看见差异不代表可以猜测资金结果并直接改表。

备选一为依据状态直接补票、改座位、改退款；备选二为只检测报告，本地业务恢复继续使用已确认的支付/退款协议。建议选择第二种：本周检测器不直接改交易、票和库存。已知渠道事实的正常未完成流程仍由现有自动扫描补齐；真正跨表矛盾或 manual_required 只报告并提供人工核查步骤。

新增 `consistency` 业务包，通过运营 `GET /api/operations/sessions/{id}/consistency` 生成单场次报告，并以可配置调度（建议默认每 60 秒、每批 10 个场次、id 游标回绕）覆盖全部场次，异常单场次隔离，下轮重试。第一版报告不另建业务表：接口返回快照报告，后台以结构化日志记录差异/失败，进程重启后重新扫描。不得声称日志具有审计表的持久性。

每个场次在一个 REPEATABLE_READ 只读事务内检查本地订单、支付、锁/明细、座位、票、退款和核销审计，避免跨多个提交版本误报。渠道与本地独立提交的暂态不当作本地硬差异；未决/人工数量作为单独恢复信息展示，不从渠道状态直接修表。

最低规则：待支付订单/ACTIVE 锁/整组当前占用一致；已取消订单没有原锁当前占用、成功支付或票；已支付类订单恰有原成功支付、CONSUMED 锁且全部订单项出票；当前占座票必须对应 SOLD 且无 current_hold_id；SOLD 必有且仅有当前占座票；HELD 必须绑定 ACTIVE 锁和待支付订单且有明细；REFUNDING 对应未决退款、REFUNDED 对应成功退款；退款金额与原订单项一致；订单退款汇总与成功退款一致；CHECKED_IN 与唯一 SUCCESS 审计相互对应。

历史例外必须测试：旧退款成功和旧订单取消后，座位可被新订单再次 HELD/SOLD，不能要求永远 AVAILABLE；旧 FAILED 退款之后票可再次退款或核销。报告包含规则编号、对象身份、观察值、严重性及人工建议，不输出原票码/恢复 token。

## 4. 验证与演示

- 有效票、重复票、退款中/已退票、伪造码、合法签名但无原票、错场次、不存在场次和时间四边界。
- 两个入口并发扫描，只能一条 SUCCESS、两条审计；成功审计写入失败后票状态回滚，重试可成功。
- 真实退款申请持锁跨入场开放边界、退款成功/失败通知与核销竞争，检查互斥和旧码不能影响重售新票。
- 查询角色、分页、过滤、摘要不泄露原票码；数据库约束阻止重复 SUCCESS。
- 正常闭环检测无差异；显式 SQL 故障夹具逐条检测；并发提交时保持一致快照；历史回流重售无假警报；调度失败可重试。
- 从固定种子执行购买、单票退款、回流重购、核销、旧码/重复拒绝、审计与一致性报告。真实 HTTP 演示不修改生产 Clock、不直接修改业务事实；时间跨越由受控测试时钟验证。
