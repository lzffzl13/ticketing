### 已确认规则直接沿用

- 手选不强制连座；推荐组合校验连座。两者都验证最新可售资格和新孤座规则。
- 普通锁座和支付期限为 15 分钟，整组成功或整组回滚。
- 成交价格和座位名称来自后端快照，请求不能指定价格或消费者身份。
- 一个订单对应一组锁及多个锁明细；锁明细没有独立业务状态，结束后保留历史。
- 支付明确失败不会自动取消订单，截止前允许重新支付；支付状态未知不能释放座位。
- 演示账号区分消费者、运营人员和核销人员，接口同时校验角色和数据归属。

`PROJECT_PLAN.md` 原第四周“支付失败后释放锁座”与已确认的状态迁移第 6.3 节冲突，本次将计划对齐为“明确失败允许截止前重试；安全取消后释放”。这沿用已有决定，不新增失败即取消规则。

## 2. Q-04：为什么只锁所选座位不够

同一段 1–5 全可售：甲买 1、2，乙买 4、5。甲单独购买剩 3–5，乙单独购买剩 1–3，都不产生孤座；如果两人同时按旧布局通过规则，再分别更新互不重叠的座位，最后剩下孤座 3。`WHERE seat_status='AVAILABLE'` 能阻止同一个座位卖两次，却不能单独保护这个跨座位规则。

同时，下单读取 ON_SALE / 票档启用后，运营人员可能立即暂停或关闭票档。库存规则和销售开关必须有共同的并发边界。

| 方案 | 能解决什么 | 代价与缺口 |
| --- | --- | --- |
| 仅对所选座位条件更新 | 防止重叠座位重复占用；同事务支持整组回滚 | 不保护邻座孤座判断，也未协调销售开关，不能作为完整方案 |
| 锁完整相关分段，协调场次管理 | 同段请求串行，不同段可并行 | 要定义稳定分段标识、多段加锁顺序及管理协调协议；比当前模型复杂 |
| **场次行锁 + 最新重验 + 条件更新（已确认）** | 复用现有管理锁，保护整场布局与销售资格判断 | 同场次库存写操作串行，有明确吞吐上限，先测量再决定是否细化 |
| Redis 原子锁座 + MySQL 落单 | 可作为第七周对照候选 | 仍要保护邻座与销售开关，并处理跨存储失败、补偿和重建；暂无收益证据 |

### 已确认的写入协议

2026-10-08，负责人先确认场次行锁、锁内最新重验及整组条件更新，随后确认幂等和时间边界，最后在登录比较后表示全部采纳并授权开始。当前锁 ID、六表、完整订单事务、READ COMMITTED 和模块边界一并接受，见 [ADR-0012](../decisions/0012-order-hold-schema-and-transaction.md)。

MySQL 为权威存储。`session_seat` 的库存状态与当前锁 ID 是当前占用事实；`seat_hold` / `seat_hold_item` 表达整组状态、期限和历史。不是两套可以独立修改的库存。

- 所有会改变本场次 AVAILABLE 集合的操作，包括下单、取消、超时和退票回流，先取得 `session` 行的 `FOR UPDATE` 锁，再读取规则所需数据、校验和写入。
- 支付出票也遵循相同顺序，以协调持有者与订单状态；**支付模拟器调用放在本地事务外**。
- 新交易写事务显式采用 **READ COMMITTED**。取得场次锁后读取当前票档和完整座位布局，再执行共用规则。第三周的只读 REPEATABLE READ 查询保持原方案。
- 不能把已有 `SeatQueryService` 的只读结果传入写事务当成最终依据，也不能在 REPEATABLE READ 事务先普通查询建立旧快照、等待场次锁后继续依赖旧快照。
- 统一锁顺序为场次 → 已有订单 → 锁记录 → 按座位 ID 升序更新座位。新下单先插入订单与锁；后续处理根据不可变的 session_id 定位，再在场次锁内重读订单。
- 每个库存更新仍带 `session_id`、期望状态及当前持有者条件，并检查影响行数。任一不符抛异常，整个事务回滚。
- 锁等待超时或死锁必须回滚并返回可重试错误；客户端以同一幂等键重试。首版不在持锁事务内无限重试。

场次行锁只是所有写入口遵守的协调协议，不会自动锁住其子表，也不会阻止直接绕过服务的 SQL。数据库行约束提供最终占用兜底，跨对象关系由本地事务维护并在后续一致性检查中检测。不同场次不用同一场次锁；普通座位图和推荐查询不取得该写锁。

上述读取语义依据 [MySQL 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)和[一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。场次行锁、锁后最新重验与 READ COMMITTED 写事务均已确认。

## 3. Q-05：固定账号与演示令牌

业务问题是让后端知道“谁在下单”，并让 consumer1 无法读取 consumer2 的订单。只接受请求中的 customerId 或 X-User-Id 没有身份验证能力。

### JWT、传统 Session 与本项目草案的区别

负责人本轮澄清比较的是通用登录机制，本项目尚未编写登录代码。三种机制都可以先校验账号密码，主要区别在之后如何识别请求身份：

| 机制 | 客户端持有什么 | 后端如何确认身份 |
| --- | --- | --- |
| 传统 Servlet Session | Session ID，通常由 Cookie 携带 | 根据 ID 找服务端会话，读取其中的登录身份；会话可由内存或共享存储维护 |
| 常见的签名 JWT | 包含身份/期限声明及签名的令牌 | 校验签名和相关声明后识别身份；仅做令牌本地验证时不必查登录会话，撤销等能力可能另加服务端记录 |
| 本项目随机令牌草案 | 不含可解析用户信息的随机字符串，请求头以 Bearer 携带 | 对字符串计算摘要，查询 MySQL 令牌与账号，检查过期、停用和角色 |

本项目草案本质上仍是服务端会话方案，和传统 Session 有同样的“凭编号查服务端状态”思路；选择显式 Bearer 头和数据库摘要表，而非 Servlet HttpSession 的会话对象/常见 Cookie 路径。它不是一种比 JWT/Session 更新的登录原理。

Cookie 或 Authorization 是凭证携带方式，JWT 是令牌格式，Spring Security 是实现认证与权限检查的框架，这些不是互斥的同一层选项。框架可以支持 Session、JWT 或本项目的随机令牌。禁用 HttpSession 不代表系统完全没有服务端登录状态，本草案的状态保存在 MySQL。

草案收益是复用现有 MySQL，令牌关联与有效期直观，删除令牌记录或停用账号后后续验证可立即拒绝；代价是每次带令牌的受保护请求增加身份查询并依赖数据库。选择 JWT 也可以满足 MVP，不把随机令牌描述成安全或性能上的普遍优越方案。比较依据见 [Spring 会话持久化](https://docs.spring.io/spring-security/reference/servlet/authentication/persistence.html)、[JWT 验证](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html)及 [Bearer 使用规范](https://www.rfc-editor.org/rfc/rfc6750.html)。

| 方案 | 取舍 |
| --- | --- |
| 配置静态 Bearer 令牌 | 实现最少，但没有正常登录入口，轮换和停用主要依赖配置 |
| **固定账号密码登录 + 随机不透明 Bearer 令牌（建议）** | 每次请求通过数据库摘要查账号，容易解释角色、过期与归属；增加两张小表和一次身份查询 |
| JWT | 减少令牌查库，但增加签名、密钥、声明和失效处理；本项目暂无收益证据 |

建议采用 Spring Security 的过滤链和认证上下文，配合自定义不透明令牌验证；版本沿用 Boot 依赖管理。身份放入认证上下文，业务服务使用可信账号 ID，禁止从下单 JSON 接受账号 ID。框架背景见 [Spring Security 认证架构](https://docs.spring.io/spring-security/reference/servlet/authentication/architecture.html)。

- 固定种子沿用 `consumer1`、`consumer2`、`operator1`、`checker1`；登录名建议仅使用小写 ASCII，输入统一转为小写后查询；不开放注册、角色编辑或找回密码。
- 密码使用 BCrypt 摘要保存；演示密码由本地种子配置提供，不放进 Flyway 迁移或日志。
- 登录成功生成 32 字节安全随机令牌，返回原值；数据库只保存 SHA-256 摘要。令牌建议有效 2 小时，过期或账号停用返回 401；不做刷新和完整生命周期管理。
- Bearer 头是唯一认证来源，不使用 Cookie 会话；无服务端 HTTP Session。CSRF 配置按这一前提处理。
- 登录、健康检查、Swagger/OpenAPI 与现有公开只读场馆/场次/座位查询可匿名访问；未知路由默认拒绝。
- 现有场馆/模板/演出/场次的管理写接口全部需要 OPERATOR；下单及个人订单接口需要 CONSUMER。CHECKER 暂没有核销业务入口。
- 登录失败、令牌失效使用统一 401；已登录但角色不匹配 403；订单不存在或不归当前消费者统一 404。
- 种子和已有管理演示脚本须同步先登录取得运营令牌；测试不得靠关闭安全过滤链通过。RequestIdFilter 要覆盖认证错误，401/403 也返回现有响应格式和请求编号。

## 4. Q-11：新下单的时间边界（已确认）

负责人于 2026-10-08 明确采纳本节建议，记录 [ADR-0011](../decisions/0011-order-cutoff-before-admission-closes.md)。

核心用例要求结束后的场次不能继续购票，但第二周明确没有实现售票时间窗口；session 目前也没有 ends_at 或 sales_close_at。只校验 ON_SALE 会让过去的演示场次继续接单，不能假设运营人员一定及时暂停。评审前尚未定义售票截止；现在已采用 ADR-0011 的入场截止前 15 分钟下单边界。

| 方案 | 取舍 |
| --- | --- |
| 只依赖手动暂停 | 无需增加逻辑，但忘记暂停的过期场次仍可接单，不满足用例 |
| 入场截止前可下单，期限取 min(创建时间 + 15 分钟, 入场截止) | 可支持更晚的购买，但会把已确认的完整 15 分钟改为“最多 15 分钟” |
| **保留完整 15 分钟，以入场截止反推最后下单时刻（已确认）** | 不增加字段，仍给足 15 分钟；代价是入场截止前最后 15 分钟不再接受新订单 |
| 新增独立售票截止字段 | 配置更灵活，但增加时间字段、管理及跨窗口约束，首个闭环复杂度更高 |

在取得场次锁后读取一次 Clock，只有 `now + 15 分钟 <= admission_close_at` 时才能新建订单。恰好等于边界时允许，晚一个数据库微秒就拒绝；订单支付截止仍为 now + 15 分钟。在该规则下，最后一张订单的支付截止可以恰好等于入场截止，新支付仍严格要求 now < payment_expires_at。等待场次锁跨过边界的请求必须按取得锁后的时间拒绝。

重复成功请求返回原订单，不按新下单时间规则再落单或续期。截止前已受理支付的迟到结果仍按已确认规则处理，不能因此延长入场窗口；支付确认延迟仍可能导致无法及时入场，该场景在后续支付闭环说明，不在这里虚构保证。Q-11 已解决。

## 5. 已确认的第一个闭环表结构

以下六张新表及 session_seat 扩展已确认并落地于 V2。SHA-256 摘要采用 CHAR(64) ASCII 二进制排序保存十六进制字符串，便于 Java/MyBatis 映射；与原草案 BINARY(32) 表达相同摘要，不改变幂等或令牌验证语义。

| 表 / 修改 | 关键字段与约束 |
| --- | --- |
| account | BIGINT id；唯一 login_name VARCHAR(64)，限定小写 ASCII；password_hash VARCHAR(128)；role ∈ CONSUMER/OPERATOR/CHECKER；enabled；created_at / updated_at |
| demo_login_token | token_digest CHAR(64) ASCII 二进制排序主键；account_id 外键；created_at / expires_at；expires_at > created_at；账号和到期时间索引。允许同账号多个未过期令牌 |
| customer_order | BIGINT id；唯一 order_number VARCHAR(36)；customer_id / session_id 外键；selection_mode ∈ MANUAL/RECOMMENDED；order_status；total_amount DECIMAL(12,2) > 0；payment_expires_at > created_at；idempotency_key VARCHAR(64) ASCII 二进制排序；request_digest CHAR(64) ASCII 二进制排序；时间戳。唯一(customer_id, idempotency_key)、唯一(session_id, id)，按消费者/时间及状态/截止时间索引 |
| order_item | BIGINT id；order_id / session_id / session_seat_id；区域代码与名称、排、座号、票档 ID 与名称、成交价快照；created_at。唯一(order_id, session_seat_id)；复合外键确保订单和座位属于同一场次；成交价 DECIMAL(10,2) > 0 |
| seat_hold | BIGINT id；order_id 唯一；session_id；hold_status ∈ ACTIVE/CONSUMED/RELEASED/EXPIRED；expires_at > created_at；时间戳。复合外键关联同场次订单，唯一(session_id, id)；到期扫描索引。ACTIVE 不因时钟到点自动变成 EXPIRED |
| seat_hold_item | hold_id / session_id / session_seat_id；created_at；主键(hold_id, session_seat_id)。复合外键约束同场次锁和座位；不设置独立状态，不对历史 session_seat_id 加永久唯一约束 |
| session_seat 扩展 | current_hold_id 可空，复合外键(session_id, current_hold_id)关联 seat_hold；补唯一(session_id, id)供复合外键使用；CHECK：HELD 当且仅当 current_hold_id 非空，其他状态为空 |

订单状态使用已确认的 PENDING_PAYMENT / PAID / CANCELLED / PARTIALLY_REFUNDED / FULLY_REFUNDED / COMPLETED 语义；第一个闭环只创建 PENDING_PAYMENT，不提前实现其他迁移。支付和电子票不塞进订单状态字段，后续独立评审表结构。

只有 `session_seat.current_hold_id` 指向的 ACTIVE 锁才持有 HELD 座位。一个库存行只能指向一个锁；历史订单、锁明细可以多次关联同一个座位。锁内的全部座位、订单项及期限相同关系由创建事务检查，不能声称一条外键已证明所有跨表不变量。

所有时间由应用 Clock 提供，以 UTC 微秒精度保存。创建订单时取同一时间，订单支付截止与锁期限都为创建时间 + 15 分钟。等待场次锁的时间不提前扣掉这 15 分钟。令牌期限同样使用可注入时钟验证。

### 幂等语义（已确认）

负责人于 2026-10-08 在响应丢失例子讲解后明确采纳本节建议，记录 [ADR-0010](../decisions/0010-idempotent-order-creation.md)。

讲解例子：10:00 消费者提交一组座位，服务器创建订单 O-001，支付截止 10:15；响应在网络中丢失。10:01 再次提交同一次购买，系统应返回 O-001 及原截止 10:15。如果只按座位是否可售判断，重试会因为自己的座位已经 HELD 而失败，消费者仍不知道刚才是否成功。

备选是只禁用按钮、按座位组合推断重复，或为每次购买意图使用请求编号。禁按钮不能覆盖网络重试；座位组合不能区分原订单重试与取消后重新购买。建议前端为每次购买意图生成请求编号，网络重试沿用；后端按“消费者 + 编号”持久化成功订单，并核对场次、选座方式和座位集合。代价是维护这段身份关系与冲突处理，收益是提交成功但响应丢失时仍能找到原订单。

- 键限定为 1–64 个 ASCII 字母、数字、连字符或下划线，按大小写精确比较；数据库采用相应二进制排序规则，避免默认不区分大小写带来的冲突。
- 唯一范围是“当前消费者 + 下单入口”，跨场次仍共享同一键空间。
- 规范化请求包括 sessionId、selectionMode 和升序 seatIds；先拒绝重复座位，再计算 SHA-256 摘要。调换座位顺序仍是同一请求。
- 相同键、相同请求返回同一订单当前状态和原截止时间，不能续锁或再落单，即使订单后来到期或取消。
- 键已关联成功创建的订单时，相同键、不同场次/选座方式/座位集合返回 409 IDEMPOTENCY_CONFLICT，不覆盖原订单。
- 校验失败或事务回滚不保留成功订单和幂等记录，未形成订单的同键请求可以再次尝试；此方案不永久绑定失败请求的内容。客户端改变购买意图时仍生成新键。这里只持久化成功创建的结果，不新建通用请求状态机。
- 若客户端不确定服务器是否已创建订单，重试必须保留原键及原内容，不能因网络超时直接换键。已创建订单的键持续绑定原购买，即使之后取消或到期；确实重新购买使用新键，再走完整库存校验。

### 事务步骤

1. 认证消费者，校验并规范化请求。若已有同键订单，核对摘要并返回；这是重放，不重新检查场次是否仍在售。
2. 开启 READ COMMITTED 写事务，调用 catalog 的服务取得场次行锁，在锁内再次查同键订单，消除同场次重复请求竞争。
3. 读取场次、票档和完整库存，检查 ON_SALE、ADR-0011 已确认的下单时间边界、所属关系、票档启用、每个所选座位 AVAILABLE；调用 inventory 共用规则检查手选/连座与新孤座。
4. 从后端快照计算价格，写订单、订单项、ACTIVE 锁及锁明细。按座位 ID 升序执行带 AVAILABLE / current_hold_id IS NULL 条件的 HELD 更新，写入本锁 ID 并核对数量。
5. 同一事务提交，返回订单；任一步异常全部回滚，不留下半张订单或部分锁定。不能让下层另开独立提交事务。
6. 相同消费者、同一键却选不同场次时，两边场次锁不会互斥；由唯一(customer_id, idempotency_key)最终仲裁。失败事务先完全回滚，再在新的事务/事务外读取已提交胜者并核对摘要。不能在已失败事务内吞掉唯一键异常后继续提交。

提交成功但响应丢失时，同键重试找到原订单；提交前进程异常时数据库回滚。不会在第一个闭环内使用 Redis、内存过期计时器或异步任务作为锁座事实来源。

## 7. 已确认的模块职责

新增 identity 与 trade 业务包。identity 提供登录、账号和认证身份；trade 编排订单事务并调用 catalog 的销售上下文服务与 inventory 的规则/占用服务。catalog / inventory 不反向依赖 trade 或身份模块内部实现，跨模块不访问 Mapper。

inventory 管理当前座位占用和锁组；trade 管理订单与成交快照。catalog 提供的写用销售上下文明确要求调用方事务，取得场次锁后返回最新状态和启用票档。数据库关系不会被当成直接访问别的模块 Mapper 的理由。
