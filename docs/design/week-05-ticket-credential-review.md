## 1. 从一张已支付订单开始

下面的编号和时间只用于讲解，不是本轮实际演示数据。

消费者小林在 10:00 为场次 S1 购买 A1、A2，创建原订单 O1，支付截止为 10:15。10:02 发起原支付 P1，模拟渠道确认 P1 成功。应用通过成功通知或主动查单，在已有的同一个本地事务中完成：P1 为 SUCCEEDED、O1 为 PAID、锁为 CONSUMED、A1/A2 为 SOLD，为两个原订单项分别签发电子票 T1、T2，票状态均为 VALID。

此时支付与出票已经成立。小林随后点击“查看 T1 的入场码”，本轮要解决的是如何为**既有电子票 T1**提供一个可扫描的凭证；重新查看不创建订单、不重新支付，也不重新出票。

### 场景一：有人只知道票号，或修改了二维码

现有本人查询已经返回 T1 的票号，它目前只是记录标识。若核销入口以后直接接受这个票号，知道票号的人就能提交它。把票号变成二维码图片，或者做一次 Base64 编码，都没有增加证明能力。

需要决定：凭什么相信提交者拿到的字符串确实是系统为 T1 提供的凭证？可选择数据库保存的独立随机秘密，也可选择带密钥校验值的字符串。对后者，修改票号而保留原校验值，应当验证失败。

### 场景二：真二维码被复制

小林截图保存了 T1 的完整二维码，别人拿到了同一截图。无论随机凭证、HMAC 还是公私钥签名，复制后的内容都仍然与原码相同。静态二维码不能识别“哪个手机才是原持有人”。

本 MVP 已确认在线核销：第六周通过当前票状态的原子迁移，保证最多一次入场。谁先提交真实凭证，谁就可能先核销；本轮不承诺阻止截图抢先使用。若要解决这一点，需要另行评审动态码、设备绑定或实名查验，不在本轮增加。

### 场景三：原票退票后，原座位卖给另一个人

沿用原订单 O1、原支付 P1 和原票 T1。以后小林在入场开放前申请退 T1：T1 进入 REFUNDING，暂停入场；退款成功后，T1 为 REFUNDED，A1 回流。另一位消费者创建新订单 O2、成功支付 P2，购买 A1 后得到全新的票 T3。

此时扫描原截图必须找到**原票 T1**并拒绝，不能根据“A1 目前又是 SOLD”去放行，更不能把旧码转向 T3。即使原码的校验值仍然正确，也不代表原票仍可入场。

若退款明确失败，既有规则允许 T1 从 REFUNDING 恢复 VALID；原码是否随之重新可用，需要在 Q-07 说明，见第 6 节的建议。退款流程本身随后单独评审。

### 场景四：发布新密钥时，消费者已经保存了旧截图

T1 的截图由 K1 生成。应用后来改用 K2。普通轮换应让合法旧截图在原场次结束前继续可用；若 K1 已泄露，则继续信任所有 K1 票码会保留伪造风险，需要撤销 K1，并让消费者重新查询原票的码。

“正常替换但兼容旧码”与“泄露后撤销旧码”是两个不同的业务选择，不能只写一句“支持密钥轮换”。

## 2. 已确认规则与实现事实

本轮沿用以下规则，不重复评审：

- MySQL 保存电子票当前事实；订单、支付、场次座位、电子票分别建模状态。
- 一个订单项永久对应至多一张票；回流重售创建新订单项和新票，旧票不复活。
- VALID 还须满足当前核销场次及 `admission_open_at <= now < admission_close_at` 才可入场；REFUNDING 暂停，REFUNDED / CHECKED_IN 为终态。
- 第六周才实施正式核销、原子状态迁移、所有尝试的审计，以及完整退款/核销入口竞争。
- 本人查询使用已登录消费者身份，校验订单归属；他人数据与不存在统一返回 404。登录令牌有效 2 小时，与票码是不同凭证。

已核对的代码边界：

| 位置 | 当前事实及约束 |
| --- | --- |
| `src/main/java/com/ticketing/ticketing/TicketModels.java` | 票记录只有 ID、随机票号、订单项/订单/场次/座位关联、状态与签发时间；没有票码、kid、签名或凭证版本 |
| `src/main/java/com/ticketing/ticketing/TicketService.java` | UUID 票号标识原票；出票以 MANDATORY 加入上层事务 |

## 3. 方案比较

以下三个主要方案都能服务于在线核销；都必须再查原票当前状态，且都无法单独阻止完整截图被复制。

| 方案 | 怎样识别真实凭证 | 收益 | 代价与本项目适配 |
| --- | --- | --- | --- |
| A. 独立高强度随机凭证，在线查数据库 | 每张票另发随机秘密，提交值与数据库保存值或摘要匹配 | 不需要全局签名密钥；可按单张票撤销、更换秘密；方案成立且可用于本项目 | 若只存摘要，重启后无法从摘要恢复原码供本人重复查看；须选择受保护的可恢复存储，或定义重新签发/旧码撤销规则。增加凭证持久化与既有票补发设计 |
| B. 最小载荷 + HMAC-SHA256 校验值（建议） | 服务器用秘密密钥为原票号计算校验值，接收时用同密钥复算验证 | 可从既有票随时生成，正常查询不用写库；无须修改既有出票事务或回填历史票；JDK 提供 HMAC | 要管理密钥与旧码兼容；持有密钥的一方既能验证也能伪造；全局泄露影响该密钥下的票码 |
| C. 最小载荷 + 公私钥签名，如 Ed25519 | 私钥签名，公钥验证 | 可以让独立验证方只有公钥，减少分发签名能力 | 当前在线核销仍由同一后端查库，暂时没有独立验证方的收益；多出公私钥配置和轮换。以后即使验签可离线，也不能据此判断实时退款和重复核销 |

直接使用现有票号作为秘密也能形成一种凭编号访问的方案，但现票号已经按普通记录标识返回并用于演示，不建议将它突然提升为入场秘密。随机票号本身难猜不等于其既有暴露面已经满足票码要求。

**建议 B 的理由来自当前边界**：单体后端、在线查库、已有持久化电子票、本人可多次查看、本轮保持一条小闭环。它不依赖“签名后就不用查数据库”这一错误前提。若更重视首版按单票更换泄露码，方案 A 值得选择；本轮建议暂不增加这种业务能力。

## 4. 建议载荷与真实性验证

### 4.1 二维码内容

建议二维码只编码一段文本，示意如下（不是可用凭证）：

```text
TKT1.<kid>.<ticketNumber>.<mac>
```

| 内容 | 目的 |
| --- | --- |
| `TKT1` | 固定票务入场用途及格式版本，避免与登录等凭证混用 |
| `kid` | 非秘密的密钥编号，让后端知道选哪把密钥验证 |
| `ticketNumber` | 绑定不可复活的原电子票；不按座位编号寻找当前新票 |
| `mac` | 对前三段完整原文计算 HMAC-SHA256，输出完整 32 字节的无填充 Base64URL 编码 |

建议固定格式：四段且只能四段；`kid` 为 1–32 位 ASCII 字母、数字、下划线或短横线；票号为规范小写 UUID；mac 为规范 43 字符 Base64URL；总长度最多 256 字节。HMAC 输入为前三段及原有点分隔符的 UTF-8 字节，不做 trim、大小写转换或重排；非法和非规范编码直接拒绝。算法固定在服务端，不接受二维码传入的算法、密钥地址或文件路径。

载荷不包含姓名、账号、手机号、订单金额、座位名称、登录令牌、票状态或可自行延长的有效期。票号可见，HMAC 提供完整性和来源校验，不提供内容加密；完整票码本身仍需保密。

建议不另放 `exp`：本 MVP 没有短周期动态码要求，允许入场的时间以数据库场次窗口为准。登录 2 小时与支付 15 分钟都不作为票码期限；入场截止后即使 mac 正确，也不能入场。

### 4.2 后端验证逻辑与第六周衔接

```text
核销人员已登录，并选择当前场次
→ 限制输入长度，严格解析格式与固定版本
→ 仅从受信配置按 kid 取可验证密钥；未知/撤销编号拒绝
→ 复算 HMAC，用适合摘要的等时比较方法检查
→ 按 ticketNumber 查询原电子票；找不到则拒绝
→ 从数据库核对原票的场次、当前状态、入场窗口
→ 第六周在正式核销事务中重验并争夺 VALID → CHECKED_IN
→ 按第六周审计契约记录本次尝试
```

验证 HMAC 成功只证明它匹配受信密钥下的内容，前提是密钥未泄露。已有真实票号、正确 mac、VALID 状态、正确场次与时间窗口缺一不可。只读查询得到的状态不能预先授权后续入场；第六周仍需在实际核销写入处重验。

本轮建议只交付内部凭证生成/验证组件和测试，不新增公开“验码即有效”接口，也不提前提供改变票状态的核销接口。第六周失败分类、幂等、事务与审计一并评审；无效码也应在那时进入完整审计流程。

## 5. 建议密钥管理与轮换

以下是本地演示环境的具体建议，不宣称具备生产密钥管理体系。

### 5.1 生成、配置与重启

- 每把密钥使用安全随机源生成独立的 32 字节，不用账号密码、票号、固定随机种子或手写口令；二维码密钥不与登录、模拟支付或其他用途共享。
- 配置包含一个当前签发编号 `activeKid` 和受信密钥集合。当前编号用于新生成的票码；其余保留项仅供验证。相同 kid 永远不改配另一份秘密，轮换使用新编号。
- 本机通过被忽略、限制文件权限的本地秘密配置注入；密钥不写入源码、迁移、种子、构建产物、公开示例、终端输出或日志。提供不显示秘密的首次生成方式及本机受控备份说明；测试使用独立且只限测试的密钥。
- 进程重启读取相同秘密。启动发现当前编号不存在、密钥缺失/长度错误、编号重复或格式非法，应明确失败并给出不含秘密的配置错误；不生成临时密钥凑合启动。这会影响应用启动可用性，需要在运行说明中交代。
- 首版通过修改受控配置并重启生效，不增加自动轮换服务、热加载或新中间件。运行期间图片生成失败只影响本次查询，不更改支付与票记录。

### 5.2 普通轮换：新码用 K2，旧截图继续兼容

1. 在本地单实例演示中停止所有仍用 K1 签发票码的本项目进程，避免旧签发者继续产生新码。
2. 在停签后读取**所有既有电子票关联场次**的最大 `admission_close_at`，作为 K1 的保守保留上界，记录编号、停签时间及上界，不记录秘密。由于没有每次生成票码的持久日志，不能假装知道 K1 精确签过哪些票。
3. 配置 K2 为当前签发项，K1 为只验证项，再启动。T1 重新查询得到 K2 码，K1 旧截图仍可验证；两者最终都绑定 T1，因此不会增加一次核销资格。
4. `now < 上界` 时必须保留 K1；`now >= 上界` 时才可移除 K1 并重启，相等时因入场窗口已结束即可退役。没有任何既有票则可立即移除；查询失败或保留上界不明时继续保留，不能按固定几天或登录令牌期限猜测删除。若曾重新启用 K1 签发，必须重新计算上界并延长记录。详细公式与例子见 ADR-0017。

这是宁可多保留一些验证密钥的保守方案。既有已开售场次窗口不可随意延长的规则继续适用。由于按需生成时不保存 kid，本轮不增加凭证表或轮换表；操作记录保存在本机受控接续文件，公开文档只描述步骤。未来多实例不停机轮换需另行设计，本轮不宣称已支持。

### 5.3 密钥泄露或丢失：撤销后重新查询原票

若 K1 疑似泄露，停止旧签发进程，换用 K2，并从所有验证配置中移除 K1。此后 K1 票码全部拒绝，不走普通兼容宽限；合法消费者登录后重新查询原票 T1，得到 K2 码。原订单、原支付、票号与票状态不改变。

生效以所有旧进程停止、对外服务进程已加载新配置为准；仅改磁盘或仅切 activeKid 不算撤销。新验证器按旧码中的 K1 查不到受信密钥，立即拒绝，不回退接受票号，也不跳过验真。已撤销编号永久记录并禁止重新加入；更具体的操作与验证要求见 ADR-0017。

若密钥只是丢失，可先从受控备份恢复；无法恢复时按换钥与旧码失效处理。撤销 K1 后不能通过回滚旧配置重新信任它。检测启动配置错误依靠明确的启动失败；处理泄露依靠运营执行上述撤销/换钥流程，本轮不新增自动泄露检测器。

负责人已接受的代价：紧急撤销会使合法旧截图失效，消费者必须重新取码。单张完整票码被泄露时，本方案没有“只撤销这一张码但原票仍有效”的入口；已退票/核销仍按票状态拒绝。若首版要增加单票换码或动态码，应重新比较 A 或引入单票凭证代次，不能在实现中暗加。

## 6. 票状态变化后，旧码怎样处理

以下为 Q-07 的建议语义；状态迁移本身沿用已确认规则，尚未实现的退款与核销不能在本轮宣称完成。

| 原票当前事实 | 旧码的处理建议 |
| --- | --- |
| VALID，尚未到入场开放 | 允许本人提前查看并保存码；正式核销须拒绝过早入场 |
| VALID，在本场入场窗口内 | 真实性验证通过后，仍由正式核销条件更新争夺一次成功权 |
| REFUNDING | 暂停入场；不能因截图仍带正确 mac 放行 |
| REFUNDING → VALID，退款明确失败 | 同一原票恢复资格，未撤销密钥下的原码可恢复使用；无须新支付或新票 |
| REFUNDED | 原码永久不能用于入场；回流重售的新票有全新票号 |
| CHECKED_IN | 原码不能再次入场；多份截图/不同密钥生成的码也不会增加次数 |
| 入场截止已到 | 不允许入场，即使票仍为 VALID 且 mac 正确；不由查询擅自写成另一票状态 |
| 正常轮换，旧密钥仍受信 | 原码继续验证，但不绕过以上任何状态或时间规则 |
| 密钥紧急撤销 | 原码无法通过真实性验证；合法消费者重新查询原票取得新码 |

建议本人票记录查询继续展示历史状态；新增取码入口只为 `VALID` 且 `now < admission_close_at` 的本人票生成凭证，其他状态保留记录但不返回可展示的码。出票后、入场开放前可提前取码；不要求等到当天开放窗口。

## 7. 确认后的最小实现范围与接口草案

本节为评审时的接口草案，现已随第 9 节获确认并落地；实际入口和执行证据见票码导读及第五周周报。

| 入口 | 建议行为 |
| --- | --- |
| 已有 `GET /api/orders/{id}/tickets` | 保留本人票记录查询，历史票仍可见，不自动写库或重新出票 |
| 新增 `GET /api/orders/{orderId}/tickets/{ticketId}/credential` | CONSUMER + 本人订单 + 票属于该订单；返回原票标识、当前票状态及凭证文本 |
| 新增 `GET /api/orders/{orderId}/tickets/{ticketId}/qrcode` | 同样校验，返回由同一生成规则产生的 `image/png`；图片只负责承载文本 |

建议查询规则：未登录 401，角色错误 403；订单不属于本人、票不存在或票不属于路径中的订单统一 404；本人票非 VALID 或已达入场截止返回 409，并给出明确业务错误。返回票码文本和图片均设置 `Cache-Control: no-store`，票码不放 URL 参数或普通日志，不借票码获取消费者身份。业务使用安全传输；当前本机 HTTP 演示边界沿用现有环境。

建议由 trade 保持归属校验与编排，通过 ticketing 服务读取同一只读快照内的票及场次窗口，返回必要快照后再做图片编码；ticketing 不反向查询 trade。新的取码查询不锁库存、不创建支付、不写票、不续期，不新增迁移；在查询后发生退票，已经返回的码以后仍须依据最新票状态拒绝。

建议 HMAC 使用 JDK 标准能力；二维码图片编码采用 ZXing 的 Java 核心库，只负责文本与二维码之间的转换。依赖版本在实施时核对并固定，不改项目技术基线、不增加服务。消费者需要的座位名称与价格继续取订单项快照，不取可变场馆模板。

范围止于：本人取码、二维码图片、内部严格验证、密钥配置与可重复演示。正式核销/审计仍属第六周，退款结构与渠道处理随后单项评审；不扩展候补、动态码、转赠、离线核销或额外中间件。

## 9. 已确认的决策集合

1. 选择方案 B：固定用途/版本、kid、原票号、HMAC-SHA256；按需生成，不给现有票表增加凭证字段，不改原出票事务。
2. 在线查原票当前状态与场次窗口；静态码允许保存，不能阻止截图被抢先使用；退款失败恢复 VALID 后原码可继续使用。
3. 每把 32 字节独立随机秘密，本机受控配置，启动校验，手工重启轮换；普通轮换兼容到保守入场截止上界，紧急撤销要求重新取码。
4. 上述本人文本/PNG 查询边界、ZXing 编码及验收范围；本轮不交付正式核销、审计与退款流程。

负责人已明确接受四项；第 3 项的准确保留期限与撤销机制已补充于第 5 节及 ADR-0017。按已确认范围实施，不将方案确认写成测试或学习验收通过。

## 10. 技术依据与本项目判断

核对日期：2026-10-15。以下资料支持基础技术事实，方案 B、载荷、接口、密钥保留上界及本地运维方式是结合项目边界提出的设计建议，并非来源直接规定的票务标准。

- [Java 21 Mac](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/crypto/Mac.html)：JDK 提供基于秘密密钥的 MAC，标准支持 HmacSHA256。
- [Java 21 SecureRandom](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/security/SecureRandom.html)：用于安全随机字节生成，不固定可预测种子。
- [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104.html)：HMAC 的基础定义与密钥长度指导；本方案使用 SHA-256 与 32 字节随机密钥，不使用该历史文档中的旧哈希示例。
- [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html)：支持明确管理密钥用途、轮换、撤销和泄露恢复。其更强的密钥存储建议不能被简化为“放进 .gitignore 就安全”；本文的本机受限秘密文件是演示范围的折中。
- [ZXing 官方仓库](https://github.com/zxing/zxing)：Java 二维码编码/解码能力，用于生成图片及解码验收，不承担票真实性判断。
