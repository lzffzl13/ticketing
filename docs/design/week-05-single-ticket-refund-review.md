# 第五周第三个闭环评审：单票退款、故障恢复与座位回流

- 日期：2026-10-15（Asia/Shanghai）
- 状态：四项建议已接受，负责人确认“可以开始编码”；决策见 [ADR-0018](../decisions/0018-single-ticket-refunds-and-durable-recovery.md)。下文保留评审比较与建议措辞，接受不代表实现或测试已完成。
- 实际起点：`codex/week5-ticket-lifecycle`，代码提交 `816a318`。本人票码闭环已实现，完整 286 项回归的执行证据见第五周周报；退款目前无表、模拟器或接口。

## 1. 从原订单、原支付和原票开始

小林的原订单 O1 买了 A1、A2 两个座位，每张成交价 200 元。原支付 P1 已成功支付 400 元，O1 为 PAID，A1/A2 为 SOLD，已签发两张 VALID 票 T1/T2。小林已经保存 T1 的二维码。

现在小林只退 T1：

1. 入场开放前受理，保存退票单 R1，同时把 T1 改成 REFUNDING；A1 仍为 SOLD，T2/A2 不变。
2. 事务结束后，以原退款编号 R1 向模拟器申请退回 200 元；“请求已受理”不表示钱已退回。
3. 模拟器独立保存最终成功与通知。通知投递到本地后，一个事务完成 R1 SUCCEEDED、T1 REFUNDED、A1 AVAILABLE、O1 PARTIALLY_REFUNDED。
4. 消费者二使用现有下单/支付流程购买 A1，产生新订单 O2、支付 P2 和新票 T3。T1 永久 REFUNDED，旧码仍只指向 T1。

若模拟退款明确失败，则 R1 FAILED、T1 恢复 VALID，A1 保持 SOLD。若渠道暂不可用或结果未知，则保留 REFUNDING/SOLD 并恢复处理，不能把超时猜成退款失败。

本轮验收旧码时检查实际旧票状态、原票绑定和取码拒绝；正式核销入口与尝试审计仍在第六周，不把内部验真成功当成可以入场。

## 2. 已确认规则：直接沿用

依据 [C8](../requirements/core-use-cases.md)、[票与退票状态机](../domain/state-transitions.md)、[领域关系](../domain/domain-model.md)及 [ADR-0017](../decisions/0017-hmac-ticket-credentials.md)：

- 本人 VALID 票可以单张独立申请；新申请在业务写锁取得后检查 `now < admission_open_at`，相等即拒绝。此前已受理的流程跨过开放时间仍继续。
- 受理时，建 REQUESTED 退票单与票 VALID→REFUNDING 同事务；处理期间暂停取码和核销资格。
- 模拟退款成功回调到达后才确认成功；退款成功、原票失效、单座回流及订单汇总同事务。
- 明确失败后退票单 FAILED、原票恢复 VALID、座位仍 SOLD；只有仍在退票截止前才能新申请。
- 同票可有多次失败历史，但最多一个进行中流程、最多成功一次；REFUNDED 永不恢复。恢复为 VALID 后，只要密钥仍受信且时间允许，原截图不需要重新出票即可继续使用。
- 同订单其他票不受单票退款影响。正式核销/审计及完整退款与核销入口竞争留第六周；不扩展候补、真实支付或中间件。

以下首次落地的金额、结构、请求身份及恢复设计需要确认，不能从上述业务规则推断为已批准。

## 3. 金额怎么退

| 备选 | 取舍 |
| --- | --- |
| 按原订单项成交价全额退、不收手续费 | 金额由已有历史快照确定，可解释、可重放；不覆盖商业退改政策 |
| 按时间阶梯扣费或允许部分金额 | 需要额外政策、舍入与累计退款约束，当前无对应需求 |
| 接受客户端传入金额 | 会把可信金额决定权交给请求方，不采用 |

建议首版按原订单项成交价全额退，不收手续费，不接受客户端退款金额。上述例子退 200 元；原支付 P1 的 SUCCEEDED 和 400 元原收款事实不改写。

## 4. 请求身份与数据结构

建议新增 V5 迁移，保留已执行的 V1–V4。继续由 trade 编排，ticketing 管票、inventory 管库存、simulator 管独立渠道事实，不引入反向模块依赖。

| 数据 | 建议持久内容与约束 |
| --- | --- |
| `refund_record` 本地退票单 | 唯一退款编号；消费者、原票、原订单项/订单/场次/座位、原成功支付、成交价退款金额；请求键、状态、受理/结果时间与失败原因；单笔恢复字段 |
| `simulator_refund` 渠道退款事实 | 原退款编号唯一，绑定原渠道成功支付、原票号与金额；PROCESSING/SUCCEEDED/FAILED；终态不可相互改写，独立事务提交 |
| `simulator_refund_notification` 通知快照 | 唯一通知编号、原退款编号、该次状态与绑定快照、生成时间和送达时间；状态快照不随之后的渠道状态变化 |

本地采用 `(customer_id, request_key)` 唯一身份：同消费者同键同目标返回原 R1；同键改订单或票返回冲突。先识别已存在的原请求，再检查新申请资格，因此截止后重放原 R1 仍能查询其结果。R1 失败后若想重新申请，使用新键生成 R2；同键永远不变成 R2。

同票不同键的并发新申请只有一个受理，其他返回“已有退款处理中”；通过状态条件更新及生成列唯一约束，保证同票至多一条 REQUESTED/PROCESSING/SUCCEEDED 记录，FAILED 保留历史且不占用资格。补充必要的唯一键/复合外键，将原票、订单项/订单/场次/座位和原支付关系绑定，避免只靠请求传参关联。

订单持久汇总状态仍为 PAID/PARTIALLY_REFUNDED/FULLY_REFUNDED；退款总额查询时汇总该订单 SUCCEEDED 退票单，不新增反复累加的金额字段。受理与失败不改变订单成功退款汇总；两张票同时退款时在订单锁内重新汇总，不能相互覆盖。

模拟器只接受后端生成的原编号和绑定，验证原渠道支付 SUCCEEDED，并在原渠道支付行锁下检查进行中及成功退款合计不超过原收款。相同退款编号重发必须具有相同绑定；不得修改金额或换票。渠道锁不跨越本地业务事务。

## 5. 事务与库存归属

| 边界 | 提交内容 |
| --- | --- |
| A：本地受理短事务 | 锁后重新校验本人、订单/票关联、成功支付、时间和 VALID；建 REQUESTED，票改 REFUNDING，同时保存首次恢复时间 |
| B：独立模拟渠道事务 | 原编号幂等受理；运营演示控制最终成功/失败，并同事务保存通知；不改本地退票/票/库存 |
| C：本地结果短事务 | 校验原通知绑定；成功则退票成功、原票失效、单座回流、订单汇总一起提交；失败则退票失败与原票恢复一起提交 |
| D：通知确认短事务 | C 已提交后才标记通知送达；确认失败允许重投，C 必须幂等；确认全部原通知已送达后，再以本地短结算事务结束该单恢复 |

建议 A/C 使用 READ COMMITTED、独立短事务，编排层不包总事务，调用模拟器或生成/投递通知时不持有本地业务锁。

遵守已确认的场次首锁协议，新增退款路径统一按 `场次 → 订单 → 原支付 → 原退票单 → 座位 → 原票` 取得所需写锁，同类多行按 ID 升序。不会先锁票再等场次。时间在取得业务锁、完成当前状态重验后读取；不能拿排队前的时间通过新申请截止检查。

支付后的旧锁组已 CONSUMED，不调用取消待支付订单的整组 `InventoryHoldService.release()`。新增单票回流操作，只对核实属于原 T1 的 SOLD 座位处理；同时核实当前占座票、REFUNDING 状态及 R1 绑定。成功后保留原 CONSUMED 锁和全部历史订单，不把已售锁组改为 RELEASED。

重复终态通知先核对同一退票单与可信绑定，然后直接返回原结果，不再次执行座位回流。即使 A1 已被新订单锁定或售出，重投 R1 成功也不得释放新占用。旧 R1 的迟到通知只处理 R1，不改变失败后新建 R2 的票状态；相同终态/旧 PROCESSING 幂等忽略，互相矛盾的终态转人工核查。

保留原支付成功结果的幂等提前返回，退款后重投 P1 不得再次出票、把订单拉回 PAID 或把已经回流的座位改回 SOLD。

## 6. 回调与恢复：保留已确认的成功节点

| 备选 | 取舍 |
| --- | --- |
| 只支持人工投一次通知 | 正常路径简单，中断后无法自动发现未完成退款，不足以完成本闭环 |
| 持久请求与通知，应用内扫描补发原请求/重投通知 | 能跨重启恢复，保留“成功回调”节点；增加每笔退款恢复信息和扫描 |
| 查单成功直接写本地成功 | 可实现，但改变当前明确的成功回调约定，本稿不建议借复用支付默认采用 |

建议第二种。退款模拟器的成功事实与原成功通知同事务保存；恢复查明已成功后，读取并重投持久成功通知，通过同一本地回调结果入口完成 C，再确认送达。不是把“受理成功”或客户端自报成功当作退款成功，也不将单独查单结果直接写成本地 SUCCEEDED。

**业务终态与通知确认完成分别判断。**C 即使已将退款单改为 SUCCEEDED/FAILED，也保留下一次恢复时间；候选包括未决退款，以及尚未结束通知确认恢复的终态单。恢复读取该原退款的持久通知并投递未确认项，全部确认后才在本地短结算事务清理恢复资格。若 D 已提交而本地结算中断，下一轮读取已确认通知，再完成结算。终态重投只核对绑定并返回原结果，不能再次改票或回流。模拟器只在首次受理/首次终态时保存对应通知，重复操作重用原事实和通知，避免结束恢复后凭空新增待投快照。

按**退票单**保存恢复信息与领取，不能借用仍只扫描 PENDING_PAYMENT 的订单支付任务。同订单两张票可分别恢复，R1/R2 的领取及失败计数互不覆盖。建议复用已有恢复参数和有限扫描方式：每轮结束 1 秒、批量 50、固定上界跨批回绕、60 秒 token 租约；正常处理中 5 秒复查，实际错误后退避 5/15/30/60/120 秒，第 6 次或持续实际异常 10 分钟转人工。参数复用是本轮建议，退款处理权归属为新增设计。

候选查询结束后逐笔处理，领取时再次检查当前状态、退避、人工标记和活动租约。旧领取不能结算新领取；可信原通知仍能幂等落地。每个事务点退出都可检测：

- A 已提交、尚未发起渠道：重启扫描发现 REQUESTED，用原 R1 补发，即使已过入场开放也不撤销已受理流程。
- B 受理后响应丢失：重试原 R1 得到原交易，不生成第二笔退款。
- B 已成功、C 未提交：渠道事实与通知保留，重投后一次性提交 C。
- C 已提交、D 未确认或响应丢失：重投原通知只返回原结果，再确认送达。
- 渠道不可用/结果未知：保持 REFUNDING/SOLD；达到人工阈值也不自动恢复 VALID 或释放座位。运营可查事实、修复和重试原编号，不能强行改成功/失败。

## 7. 建议入口与可重复演示

- 消费者：`POST /api/orders/{orderId}/tickets/{ticketId}/refunds`，仅提交请求键；本人订单退款列表/单笔查询保留历史与当前处理结果。角色和归属沿用已有登录机制。
- 运营：在 `/api/operations` 下提供模拟退款成功/失败、原通知列表/投递及单笔主动恢复。请求只定位可信持久记录，不允许客户端填写任意成功通知内容。
- 自动：独立退款扫描入口，与支付扫描各自读取自己的持久任务；复用规则和小工具，不提前抽取通用流程引擎。
- 演示：保存原 O1/P1/T1/T2/R1，重跑核对原身份；新消费者真实重购 A1 得到新 O2/P2/T3。构造不会触发新孤座拒绝的独立场次，或者明确该夹具允许制造孤座，不修改通用购票规则。

## 9. 本次需要确认的四项新建议

1. **金额**：原订单项成交价全额退，无手续费，客户端不传金额，原支付收款事实保留。
2. **结构与请求身份**：V5 本地退票、独立渠道退款及通知三表与绑定约束；消费者+请求键幂等；失败新键再申请；订单退款金额按成功单汇总。
3. **渠道与结果事务**：独立持久模拟器、原编号/原支付/原票/金额绑定与额度限制；保留成功回调节点；遵守场次首锁，短事务原子回流、终态幂等且不影响重售。
4. **恢复**：按退票单扫描/领取，沿用既有租约、批量、退避及人工参数；补发原请求、重投原通知，未知保留退款中；完成失败、重启与真实重售验证。

四项建议已由负责人确认，记录 ADR-0018 后实施这一条闭环。已确认业务规则不重复询问；实际执行证据另记第五周周报。
