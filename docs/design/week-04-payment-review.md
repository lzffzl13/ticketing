## 1. 实际起点与本次范围

本部分目标：发起模拟支付 → 查询/通知确认结果 → 最小出票与本人票查询；同时支持安全取消、可重复恢复、竞争与中断测试、完整演示及数据库锁座基线。自动超时扫描、二维码、退款和核销按后续周次推进。第四周票号仅标识记录，不作为核销凭证；Q-07 仍开放。

## 2. 已确认规则

1. 一订单允许多笔历史支付，最多一笔进行中支付、最多一笔成功支付；明确失败不取消订单，截止前可重试。
2. 新支付须订单待支付且 `now < payment_expires_at`。此前已受理支付可在截止后确认；不能因本地没收到成功通知而释放座位。
3. 回调、查单共用幂等结果入口；结果可以先于受理确认到达，终态不能倒退。
4. 支付成功、订单 PAID、锁 CONSUMED、整组 SOLD、全部订单项出票在一个 MySQL 本地事务提交。
5. 有支付尝试时，取消与超时释放须确认未支付并取得交易不会再成功的安全证明；从未创建支付尝试时可锁内直接取消。未知时保持占座并恢复。
6. 库存写入沿用场次锁、READ COMMITTED、锁后重读及条件更新；已有订单不因暂停销售或票档停用而失去支付结果确认资格。
7. 模拟器交互不能假装与本地出票天然共享一个事务；跨模块通过服务。

依据：[ADR-0001](../decisions/0001-resolve-payment-before-releasing-seats.md)、[状态迁移](../domain/state-transitions.md)、[核心流程](../domain/core-flows.md)、[ADR-0009](../decisions/0009-serialize-session-inventory-writes.md)。

## 3. 第一项评审：支付尝试与模拟器分开保存

2026-10-10：负责人要求进一步讲解后明确“采纳建议”，确认持久化、独立提交、首次受理截止及关闭记录阻止迟到发起，见 [ADR-0014](../decisions/0014-persist-independent-payment-simulator.md)。具体最低表结构继续见第 8 节；以下工程细节不能被视为后续全部已获批。

### 问题与备选

例如 10:00 下单，截止 10:15。10:14:59 模拟器受理并收款，应用在出票前退出；恢复后本地仍待支付。系统需要查回已收款事实，继续出票。内存模拟器重启后会丢失这项事实。

| 方案 | 收益 | 代价与限制 |
| --- | --- | --- |
| 内存模拟器 | 代码少，正常流程容易演示 | 重启丢失交易，无法验证收款后本地中断的恢复 |
| MySQL 持久化模拟器、独立提交（建议） | 可查回模拟结果、重投通知、验证重启恢复 | 增加表与短事务；同机同库不能模拟完整外部网络故障 |
| 单独进程或服务 | 进程故障边界更接近外部渠道 | 增加部署与测试成本；当前闭环无需拆服务 |

建议同一应用、同一 MySQL 中分表保存，每次模拟器操作独立提交。用同一支付编号关联本地尝试与渠道交易，两个状态分别表达“本地处理进度”和“模拟渠道事实”。

```text
本地短事务 A：校验身份、订单、截止；创建 INITIATED 尝试 → 提交
事务外编排：按支付编号调用模拟器
模拟器短事务 B：幂等受理，保存 PROCESSING 或返回已有终态 → 独立提交
本地短事务 C：应用受理状态或最终结果；成功时原子出票 → 提交
```

- A 成功、B 未执行：已有待恢复意图。查无交易且未到期、无取消意图时，以原编号和原内容幂等补发；已到期或取消时，关闭原编号，不能新建支付尝试。
- B 成功、C 失败：收款事实仍在，后续查单或重投通知完成 C。
- C 成功、响应丢失：原编号重试返回原结果，不重复出票。

通过不同 Spring 服务代理执行事务；编排层不持有场次/订单锁调用模拟器。独立提交仅用于模拟器事实，不改变订单、库存和票一起提交的要求。

### 同时需要评审的模拟器约定

- 发起、查单、关单使用同一编号。编号绑定订单、金额和原截止；重复发起复用原交易，内容冲突拒绝。
- 模拟器首次受理也检查原截止：取得该编号的受理权后再读取 Clock，仅 `now < payment_expires_at` 可以受理，不能用等待前的旧时间。本地 INITIATED 是已保存意图，不是渠道受理证明。首次到达已过期则建议持久保存 FAILED 和 EXPIRED_BEFORE_ACCEPTANCE 原因，重复同编号返回原拒绝；原已受理编号重试返回原交易，不重新检查受理资格。未受理的 FAILED / CLOSED 记录允许 accepted_at 为空。
- 成功与关单通过同一模拟交易行竞争，只有一个终态；截止前已受理交易可以在截止后得到结果。
- **查不到交易不等于可安全释放。** 关单对尚不存在的编号也保存 CLOSED 记录；迟到发起只能读到 CLOSED，不能再开启交易。
- 首次发起和首次关单可能同时面对不存在的编号，不能依赖锁住一个尚不存在的交易行。用支付编号唯一约束仲裁插入；唯一键失败方先回滚，在独立短事务中重读胜者，再按受理/关闭规则处理。关闭请求携带与发起相同的订单、金额和截止绑定内容，关闭记录不能成为内容校验漏洞。
- FAILED 保持终态；关单对它返回“已终结、不会再成功”的安全确认，不把 FAILED 改写为 CLOSED。成功交易只能返回已支付。
- 消费者不能提交成功状态。演示由 OPERATOR 控制，通知仅来自实际保存的交易结果。
- 延迟、重复、乱序通过保存的通知快照及可控投递复现；同通知重投和不同通知重复表达成功均不能重复出票。投递失败保留记录，可按同通知恢复。
- 渠道状态变化与通知快照在同一模拟器事务中保存，提交后才投递；本地结果事务提交成功后才标记送达。模拟器表不以本地支付表外键为依赖，保证渠道事实的独立提交。

本节方向及第 8 节最低两表结构现已获确认，模拟器发起/查单/关单、独立提交和竞争测试已完成，见 ADR-0014 与模拟器导读。该确认不扩展为后续所有新表或事务已获批；本地支付表、出票、取消和重试参数继续分项评审。

## 4. 后续评审：结构与幂等结果事务（草案）

保持已执行 V1 / V2 不变；模拟器两表先使用 V3，后续本地支付/票表采用下一版本，均在各自结构确认后执行。以下为结构方向，确认后再确定 SQL 和最终字段。

| 对象 | 拟保存内容 | 关键约束 |
| --- | --- | --- |
| payment_record（trade） | 订单、支付编号、金额、请求编号、支付状态、受理/结果时间、恢复信息 | 同订单/请求编号唯一；支付编号唯一；同订单最多一笔进行中及一笔成功 |
| simulated_payment（simulator） | 支付编号、绑定内容、原截止、受理时间、渠道终态 | 同编号唯一；终态不可覆盖；尚不存在编号也可先关闭 |
| simulated_notification（simulator） | 通知编号、支付编号、观察到的状态/时间、投递完成信息 | 保存快照与重投依据；渠道状态提交后才投递，本地结果提交后才确认送达 |
| ticket（ticketing） | 票号、订单项、订单、场次座位、票状态、签发时间 | 订单项永久唯一；仍占用座位的票唯一；退款历史票不阻碍新订单出票 |
| customer_order 扩展 | cancellation_requested_at、取消原因 USER/TIMEOUT | 取消意图不等于 CANCELLED；未知时仍待支付，但阻止新支付 |

建议支付请求以 `(order_id, request_key)` 幂等；原键始终返回原尝试，失败后用新键再发起，不续期限。事务与唯一约束共同保证一笔进行中支付，不能只靠先查后写。

trade 编排订单、支付及结果；simulator 独立保存渠道事实，不反向访问 trade；ticketing 提供加入上层事务的出票和按订单查询。本人票查询由 trade 先验证订单归属，再在同一只读事务中调用 ticketing 按订单查询，避免 ticketing 为校验归属反向访问 trade。跨模块只调用服务。

票同时保存订单、订单项、场次与座位时，需要在 V3 给 order_item 增加相应复合候选键，再由票表复合外键绑定，不能只凭 order_item_id 唯一就声称数据库防住了错误关联。具体 SQL 在结构评审确认后确定。

```text
可信通知 / 查单结果 → 定位不可变 session_id
→ 锁场次 → 订单 → 支付按 ID → 锁组（重读最新状态）
→ 核验支付编号、订单、金额及状态
→ 相同终态返回原结果；迟到 PROCESSING 不倒退；冲突终态拒绝并留痕
→ 新成功：支付 SUCCEEDED + 订单 PAID + 锁 CONSUMED
          + 整组 HELD→SOLD、清 current_hold_id + 每项一张 VALID 票
→ 检查影响行数与票数量 → 一起提交
```

座位条件更新须匹配场次、HELD 及原持有者；任一座位归属变化、订单项缺失或出票失败，整笔本地事务回滚。既有成功结果不重新检查新销售的 ON_SALE / 票档开关，也不以当前已过截止拒绝原已受理交易。

票的座位占用唯一约束须包含 VALID / REFUNDING / CHECKED_IN；不能对座位建立永久唯一票索引，否则退款回流会被历史票阻断。本轮只签发和查询 VALID 票。

## 5. 后续评审：安全取消与 Q-06（草案）

建议先在场次/订单锁内保存取消意图，阻止新支付；提交后查单、关单；最终重新取得场次、订单、支付与锁组的锁，重读支付集合和持有者。

| 事实 | 行为 |
| --- | --- |
| 从未创建支付尝试 | 锁内可直接取消并整组释放 |
| 模拟器已成功 | 统一成功入口出票，取消意图不能覆盖收款事实 |
| 所有交易确认未支付且不再可能成功 | 同事务 CANCELLED、锁 RELEASED/EXPIRED、整组 AVAILABLE、清持有者 |
| 查单/关单失败或未知 | 保持 PENDING_PAYMENT / ACTIVE / HELD，保存恢复信息 |

不能凭事务外旧查询释放。取消意图直到出票或安全取消才结束；某笔支付失败不能让新的尝试钻入。重复取消返回确定结果或仍待确认状态。

Q-06 建议参数，**尚未确认**：

- 第四周提供运营恢复入口与演示，第五周扫描复用相同恢复服务；当前不声称自动恢复。
- 恢复只处理原支付编号，不创建新尝试。主动查单；有取消意图或已到期时按结果安全关单。
- 未到期、无取消意图且查无交易时，以原编号和原内容补发原 INITIATED 意图；模拟器仍以首次受理的实际时间检查截止，不把补发视为新支付或续期。
- 保存首次未决时间、连续失败次数、下次恢复时间、最近错误分类与人工介入标志。创建意图时即保存恢复时间，避免进程退出丢失线索。
- 连续失败后的间隔建议 5、15、30、60、120 秒，以后封顶 120 秒；连续失败 5 次或首次未决超过 10 分钟，标记人工介入并暂停常规自动尝试。
- 人工介入只能检查事实、修复依赖、重做同编号恢复，不能把未知支付强改未支付或强行释放。
- 本地结果提交失败后也能重新查单应用；模拟器事实不随本地回滚。并发恢复保证幂等，扫描领取与失败计数去重在第五周接入前评审。
- 第四周并发人工恢复也不能把同一次故障重复累计而提前触发人工介入；失败次数更新须与当次恢复尝试身份绑定，具体领取协议在实现前确认。

确认后更新 PROJECT.md、开放问题及对应 ADR；当前不能把候选参数写成正式规则。

## 8. 第二项评审：模拟器最低两表结构

状态：已确认。负责人于 2026-10-10 明确“采纳两表，开始实现”，授权本节结构及同事务占号后校验截止的实现，见 ADR-0014。本节只涉及模拟器持久结构；本地支付尝试、票表、取消意图和恢复参数继续待评审。

### 为什么交易与通知分表

交易行回答“现在到底是否已支付”；通知行保存“某个时刻产生了什么消息”。例如先生成 PROCESSING 通知，后来支付 SUCCEEDED；两条通知都可以保留。先投成功再投旧 PROCESSING，才能复现自然乱序。一个状态字段无法同时表达这两个事实。

| 方案 | 收益 | 限制 |
| --- | --- | --- |
| 只保存交易，通知放内存 | 少一张表 | 重启丢通知，难以保留历史通知和复现重投/乱序 |
| 交易和通知分别持久保存（建议） | 当前事实和历史消息独立，失败后可以按通知编号重投 | 多一张小表及提交后投递步骤 |

### simulated_payment：模拟渠道交易

| 字段 | 类型方向 | 用途 |
| --- | --- | --- |
| payment_number | ASCII、区分大小写、最长 36 字符，主键 | 同编号发起/查单/关单，防重复建行 |
| merchant_order_number | ASCII、最长 36 字符 | 绑定商户订单编号，不依赖订单表外键 |
| amount | DECIMAL(12,2)，大于 0 | 绑定后端订单金额，重试内容不同拒绝 |
| payment_expires_at | DATETIME(6)，非空 | 原截止，首次受理资格判断 |
| payment_status | PROCESSING / SUCCEEDED / FAILED / CLOSED；内部 RESERVED | 渠道当前事实；RESERVED 只在未提交事务中占号，本地 INITIATED 不属于该表状态 |
| accepted_at | DATETIME(6)，可空 | 实际首次受理时间；未受理即拒绝/关闭时为空 |
| result_at | DATETIME(6)，可空 | 终态确定时间；PROCESSING 时为空 |
| failure_code | ASCII、最长 64 字符，可空 | FAILED 原因；过期拒绝建议 EXPIRED_BEFORE_ACCEPTANCE |
| created_at / updated_at | DATETIME(6)，非空 | 创建与最后状态变化时间 |

最低约束：编号及商户订单号非空、金额为正；状态只取以上值；PROCESSING / SUCCEEDED 必须有 accepted_at；RESERVED / PROCESSING 无 result_at，终态必须有 result_at；FAILED 必须有失败分类；accepted_at 非空时严格早于原截止。关闭可先于受理，因此不能要求每行都有 accepted_at，也不能要求建行时间早于截止。

编号、订单、金额和截止一经绑定不改变；重试先核对绑定内容，再返回原结果。首次发起与首次关单用唯一编号插入仲裁，失败事务回滚后重新读取胜者；取得编号的处理权后读取 Clock，再决定受理/拒绝。

为避免先写虚假的受理时间，首次建行在同一个短事务中先以 RESERVED 占号（accepted_at/result_at 均为空），取得编号后读取 Clock、改成真正的 PROCESSING / FAILED / CLOSED 并保存通知，最后才提交。RESERVED 不作为查单结果、不单独提交、不发送通知；中途失败整笔事务回滚。增加实际写入后故障测试，证明不会遗留 RESERVED。这是内部事务步骤，不新增消费者可见的支付业务状态。

### simulated_notification：通知快照

| 字段 | 类型方向 | 用途 |
| --- | --- | --- |
| notification_number | ASCII、最长 36 字符，主键 | 重投同一通知的稳定编号 |
| payment_number | 与交易主键同类型、外键 | 关联已经保存的模拟交易 |
| observed_status | 与渠道状态同范围 | 保存当时状态，不能查询后随最新交易状态重写 |
| observed_at | DATETIME(6)，非空 | 状态通知生成时间 |
| delivered_at | DATETIME(6)，可空 | 本地结果事务成功后才确认送达；空表示尚未确认 |

最低约束：非空通知编号、合法状态、交易外键；delivered_at 非空时不得早于 observed_at。索引支持按未送达及生成时间查看通知。交易状态变化与通知快照在同一模拟器事务保存，提交后投递；重复投递保留原通知编号和内容。

不在这两表中设置到本地 payment_record 的外键，不加入恢复退避或扫描领取字段；这避免将当前模拟器结构与尚未确认的本地恢复方案绑定。发送失败不确认 delivered_at，保留原通知供重投；提交成功而确认送达前中断会再次投递，因此本地结果入口必须幂等。

V3 已落地模拟器两表，并完成内部服务与 25 项真实数据库测试；后续本地支付/票结构使用下一迁移，不把尚未确认字段混入已确认迁移。消费者支付和运营 HTTP 编排入口随后续支付闭环接入，模拟器模块不反向访问 trade。
