# 第五周首个闭环：自动超时取消与支付恢复评审

- 日期：2026-10-13 起草，2026-10-14 确认（Asia/Shanghai）
- 状态：负责人回复“采纳建议，实施这个闭环”，调度方式与默认参数已接受，见 ADR-0016；实现和测试证据另列于第五周周报。
- 起点：第四周已完成安全取消、支付恢复和本轮核心代码理解检查；第五周沿用 ADR-0001 / 0015，不重新确认支付事务、退避和领取规则。

## 1. 本周范围与推进顺序

第五周目标是超时处理、票码查询、单票退票和座位回流。一次完成一个可以验证的小闭环：

1. 自动扫描到期订单与未决支付，复用已有安全取消/恢复服务。
2. 分项评审 Q-07：二维码载荷、真实性验证和密钥轮换，再实现票码查询。
3. 评审单票退票的表结构、退款模拟器、幂等及本地事务，再实现退款回流与旧票失效。
4. 补充支付/超时、重复退款、回流重售等竞争与故障测试，以及可重复演示。

正式核销接口、核销审计和一致性检查仍在第六周；第五周先验证已核销票不能退票，退票与核销的完整入口竞争在第六周补齐。不把数据库夹具验证称为已实现核销。

本文只评审第 1 项。二维码和退款涉及尚未确认的重要决策，后续分别解释和确认，不从扫描授权推断它们已经获批。

## 2. 业务问题与不变量

例如消费者 10:00 下单，原支付截止 10:15。第四周必须由运营调用恢复入口才能推进到期或中断的订单。没有人调用时，即使从未发起支付，座位也会继续 HELD。

自动任务要发现这些订单，但不能根据时间直接释放：

| 持久事实 | 自动处理的目标 |
| --- | --- |
| 10:15 到期，从未保存支付尝试 | 在现有本地事务内取消订单、结束整组锁并释放全部座位 |
| 渠道支付仍 PROCESSING | 查询并关单；渠道先成功则出票，渠道先关闭则安全取消 |
| 渠道已收款，本地尚未出票 | 查询原编号并应用成功事实，原子出票 |
| 查单/关单或出票失败 | 保持占座，保存错误与下次重试时间 |
| 连续实际故障达到人工阈值 | 暂停普通自动尝试，保留运营恢复入口 |

必须保持：支付截止不续期、未知不释放、成功优先出票、整组原子变化、重复处理不产生第二份业务结果。60 秒租约、5/15/30/60/120 秒实际故障退避、连续 6 次或持续实际异常 10 分钟转人工，均已在 ADR-0015 确认。

## 3. 调度备选与建议

| 方案 | 收益 | 代价与限制 |
| --- | --- | --- |
| 应用内定时扫描 MySQL（建议） | 复用已有订单期限、恢复时间、索引及领取协议；重启后仍可发现积压；部署简单 | 处理有扫描延迟；应用停机期间不执行；需要有界批次和失败隔离 |
| 增加延迟消息或独立调度组件 | 可按事件触发，后续能独立扩展任务执行 | 增加部署、投递、重复消费和消息丢失补偿；仍需数据库重验和漏单扫描 |
| 继续仅由运营主动恢复 | 无新增后台任务 | 到期取消与中断恢复依赖人工，不能完成第五周自动处理目标 |

建议首版采用 Spring 应用内定时扫描 MySQL，不增加 Redis、MQ 或新表。它实现的是已有恢复协议的自动触发，不能据此声称精确到秒释放或具备生产容量。

建议初始运行参数为：启动后自动启用，每轮结束 1 秒后再开始下一轮，每轮最多读取 50 个候选并逐单处理。间隔、批量和启停均通过配置调整。这里的 1 秒和 50 是保守的开发默认值，不是性能结论，也不修改 15 分钟支付期限或已确认的故障退避。

## 4. 候选与事务边界

候选查询只读，包含以下条件：

- 订单仍为 PENDING_PAYMENT，未标记人工介入。
- 没有未过期的领取租约。
- 有 next_recovery_at 时，仅在它已到期时选中；支付已截止也不能绕过故障退避。
- 无 next_recovery_at 时，支付已截止或已有取消意图才选中。必须覆盖从未发起支付的订单，它们没有恢复时间。

每次完整遍历先固定最大订单 ID 上界，各批按 ID 向前扫描，记住最后读取的 ID；到尾后回到起点并刷新上界。游标只影响访问顺序，候选资格和最终事实在 MySQL。重启丢失游标只会从头再扫，幂等与租约保护仍然有效。固定上界同时避免低 ID 持续失败堵住后方，以及新高 ID 持续进入导致旧订单迟迟得不到复查。

```text
定时触发 → 短只读事务获取有限候选 ID → 结束查询事务
         → 每个 ID 调用 recoverIfDue
         → 场次/订单锁内重读资格并领取
         → 提交本地短事务后查询原渠道编号
         → 现有本地结果事务完成出票或安全取消
```

扫描整批不包在一个数据库事务中，不持有订单/库存锁调用渠道。某个候选抛出异常时保留其持久状态，并继续处理后面的候选；数据库查询失败则记录批次错误，在后续轮次重试。

多个应用扫描同一订单时继续由现有订单级租约协调，候选 SELECT 不是领取成功的证明，也不需要为扫描增加分布式锁。

## 5. 已发现的锁内重验边界

当前 PaymentTransactionService.claim 先保存超时意图并尝试 cancelIfSafe，之后才在 claimLocked 检查人工标志与退避。候选查询之后，另一个处理者可能已经标记人工核查；若本地支付都是 FAILED / CLOSED，原顺序仍可能释放座位。

实施时应在自动入口的任何取消副作用之前，在锁内重新检查人工标志、下次恢复时间和活动租约。运营主动恢复依旧可以越过退避与人工标志，但遵守活动租约。此修正执行的是 ADR-0015 已确认的自动暂停规则，不改变运营权限或支付状态机。

即使支付已确定 FAILED / CLOSED，已过期但尚未结算的领取也要先计入中断故障。达到第 6 次阈值时暂停自动取消，不通过直接安全释放绕过人工门槛；运营核查后仍可依原编号恢复。

时间测试使用可控 Clock，不真实等待 15 分钟。并发测试使用屏障或受控挂起点，断言最终订单、支付、锁、座位和票，不能从功能测试推出吞吐能力。

## 7. 失败检测与恢复

- 订单仍保留 recent_error、next_recovery_at、consecutive_failures 和 manual_required，运营可通过已有恢复查询观察。
- 扫描运行错误写日志；后续调度继续读取持久任务。进程重启从数据库重新发现，不依赖内存定时器保存业务期限。
- 已领取后进程退出：租约到期后依照 ADR-0015 接管；旧 token 不能覆盖新领取结算。
- 达到人工阈值：修复依赖后使用原运营恢复入口，不强行释放未知支付座位。
- 没有扫描延迟或吞吐实测前，不承诺清理时延；新的调度性能实验不替代业务正确性验收。
