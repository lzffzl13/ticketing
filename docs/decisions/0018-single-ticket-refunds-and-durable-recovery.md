# ADR-0018：单票全额退款、独立渠道事实与持久恢复

- 状态：已接受
- 日期：2026-10-15（Asia/Shanghai）
- 确认：负责人对退款评审四项新建议回复“确认可以开始编码了，编码之前可以先把之前的未推送的推送掉”。
- 依据：[第五周单票退款评审](../design/week-05-single-ticket-refund-review.md)。

## 业务问题与取舍

原订单 O1 已由原支付 P1 成功购买 A1/A2，并签发 T1/T2。仅退 T1 时，必须保留其他票、原支付事实和历史；渠道退款成功后本地中断也不能丢失退款结果或再次退款。回流重售生成新票 T3，旧通知不得释放 T3 的库存。

采用 MySQL 本地退票单、独立模拟渠道退款与不可变通知三表，以及每笔退票的短事务与持久恢复。相比一次性内存调用增加状态与恢复协议，但不增加 MQ、Redis 或通用流程引擎。继续保留已确认的成功回调节点，不以受理或单独查单直接确认成功。

## 决策

1. 按原订单项成交价全额退，无手续费，客户端不传金额；原支付保持 SUCCEEDED 和原收款金额。
2. V5 新增 refund_record、simulator_refund、simulator_refund_notification，保留已执行 V1–V4。原票/订单项/订单/场次/座位及原成功支付通过绑定与数据库约束保护。
3. 消费者与请求键唯一识别申请：同键同目标返回原单，改目标冲突；明确失败后用新键申请。生成列唯一约束保证同票至多一个 REQUESTED/PROCESSING/SUCCEEDED，失败历史保留。
4. 本人 VALID 票新申请严格早于 admission_open_at，锁后读取时间。建 REQUESTED 与票改 REFUNDING 同事务；已受理流程过开放时间仍继续。
5. 模拟器按原退款编号幂等，原支付/原票/金额不可换绑；在原渠道支付行锁下验证原支付成功及进行中和成功退款总额不超收款。受理与首次终态各保存通知；重复操作重用原事实和通知，终态不可倒退。
6. trade 编排、ticketing 管票、inventory 管库存、simulator 管渠道。短事务 READ COMMITTED，依次取得所需场次、订单、原支付、退票单、座位、原票锁；同类多行升序。渠道调用不持有本地业务锁。
7. 原成功通知经统一入口应用：退票成功、原票 REFUNDED、单座 SOLD→AVAILABLE、订单部分/全部退款汇总同事务。明确失败则退票 FAILED 与原票恢复 VALID 同事务。未知保持 REFUNDING/SOLD。
8. 不复用待支付整组释放；保留 CONSUMED 锁历史。核实原票当前占座，终态重投提前幂等返回，不再回流。原支付重复结果也不重复出票或拉回订单状态。退款金额查询汇总成功退票单，不另设累加字段。
9. 每笔退票独立保存恢复信息，扫描补发原请求、重投原通知。默认每轮结束 1 秒、批量 50、固定上界跨批回绕、60 秒 token 租约；正常处理 5 秒复查；实际错误退避 5/15/30/60/120 秒，第 6 次或持续实际异常 10 分钟转人工。候选资格锁内重验，旧 token 不能结算新领取，可信通知仍可幂等应用。
10. 业务终态不等于通知确认完成：SUCCEEDED/FAILED 仍有恢复时间时继续扫描；全部原通知确认后才清理恢复资格。结果提交、通知确认、本地结算各自提交，任意中断均可幂等重试。运营可查事实与重试原编号，不能强行改结果或释放未知座位。
