# ADR-0014：持久化支付模拟器与独立提交

- 状态：已接受；负责人在进一步讲解后明确表示“采纳建议”
- 日期：2026-10-10（Asia/Shanghai）
- 确认范围：模拟器持久化、独立提交、首次受理截止、关闭记录阻止迟到发起；负责人随后确认最低两表结构并授权实现

## 背景

模拟器已收款而本地出票失败时，收款事实必须保留，供查单或重投通知恢复。本地出票回滚不能撤销模拟渠道已提交的结果，进程重启也不能丢失该结果。

本地保存 INITIATED 支付意图不代表模拟器已经受理。还可能发生支付发起尚未到达模拟器，取消先完成关单，发起随后到达的竞争；只把“查不到交易”当作未支付证明会留下释放后收款的窗口。

## 备选与取舍

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| 内存模拟器 | 实现少 | 重启丢失收款事实，不能验证中断恢复 |
| 同一应用内的 MySQL 持久模拟器 | 保留结果和可重复查询，部署简单 | 增加持久记录与独立事务；同机同库故障与真实外部渠道不同 |
| 独立进程或服务 | 可模拟更完整的外部故障边界 | 当前纵向闭环不需要增加部署复杂度 |

采用同一应用内的 MySQL 持久模拟器，每次渠道操作独立提交。

## 已确认决策

- 本地先提交支付意图，再在持锁事务外调用模拟器，最后在本地结果事务里处理受理或成功结果。
- 模拟器收款事实独立提交；本地出票失败时渠道成功记录保留。订单、锁、库存和票继续共同提交。
- 发起、查单和关单使用同一支付编号；重试不创建第二笔渠道交易。
- 模拟器首次受理也须严格早于原 payment_expires_at；本地意图不能替代受理证明。截止前已经受理的同编号交易继续确认，不续期限。
- 关单可以为尚不存在的编号保存 CLOSED 记录；迟到发起不能重开交易。
- 交易成功和关单只有一个终态；终态不能被迟到通知覆盖。
- 模拟器控制来自运营演示，不让消费者直接提交支付成功状态。

## 实施与验证边界

负责人进一步确认[支付评审第 8 节](../design/week-04-payment-review.md)的两表结构，并明确“采纳两表，开始实现”：

- simulated_payment 以支付编号为主键，绑定商户订单编号、金额和原截止；保留状态、首次受理、终态时间、失败分类与审计时间；不引用本地订单/支付外键。
- simulated_notification 保存独立通知编号、支付编号外键、当时状态、观察时间及首次送达时间；重投不改变快照，渠道状态与通知共同提交。
- RESERVED 仅在同一个未提交事务中占号；取得编号后检查实际时间，再写实际受理或终态，不能独立提交、对外返回或生成 RESERVED 通知。
- V3 只新增上述两表，旧迁移不修改。后续本地支付/票结构采用新迁移。

本次不把模拟器结构确认扩展为支付/票表、取消意图或 Q-06 参数确认。

已实现 V3、模拟器内部服务及 25 项真实 MySQL 测试。2026-10-10 13:00:14 +08:00 完整回归 190 项通过（87 unit + 103 IT）；执行证据见第四周周报，入口与关键代码见[模拟器导读](../development/payment-simulator.md)。

测试证明独立渠道提交不随调用方事务回滚、原编号重放、首次受理截止、未创建编号先关单、发起/关单并发、通知快照及部分写入回滚。尚未接入真实本地支付/出票接收器，不能把调用方事务回滚测试等同于实际出票失败恢复。
