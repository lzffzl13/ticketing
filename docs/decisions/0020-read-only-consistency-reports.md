# ADR-0020：一致快照检测与只报告修复边界

- 状态：已接受
- 日期：2026-10-18（Asia/Shanghai）
- 确认：负责人对第六周两组建议回复“两组都采纳，直接编码（推荐）”，Q-08 关闭。
- 依据：[第六周评审](../design/week-06-checkin-consistency-review.md)。

业务问题是识别本地跨表矛盾，且不把暂态或旧历史当作可直接修改当前库存的证据。比较依据差异直接补票/改库存与报告后复用既有恢复协议，选择后者。本周不新增第二套资金、出票或回流状态机，不直接按报告修表。

新增 consistency 诊断包。运营查询单场次报告；后台默认每轮结束 60 秒、每批 10 场次，固定最大 ID 跨批遍历和回绕，单场次失败隔离，候选查询失败不推进。重启重新发现，不依赖进程内游标保持正确性。参数可配置，测试禁用真实调度。

一个场次的所有本地表在同一个 REPEATABLE_READ 只读事务中读取，不混用 FOR UPDATE 或多个 REQUIRES_NEW 服务拼接快照。检查订单/明细、支付、锁/明细、当前座位、票、退款及核销成功审计。渠道独立提交到本地结果之间是合法恢复窗口，不作为本地硬差异。

旧 CANCELLED 订单和已成功退款票的座位允许被新订单 HELD/SOLD；检查原占用已结束和当前占用一致，不能要求永远 AVAILABLE。旧 FAILED 退款后允许重新退款和核销。仅因截止已过而尚未 COMPLETED 不作为硬差异；所有票实际核销/退款完成却未原子归集，属于本轮已实现事务规则的差异。

报告返回规则、对象编号、观察值和处理建议；定时任务以日志记录发现和失败。第一版不建报告持久表，日志留存受部署环境约束，演示另保存 JSON 样例；不宣称已实现外部通知平台。

自动恢复只沿用已确认的支付/退款扫描、幂等结果事务、领取 token、退避与人工门槛。跨表矛盾、资金终态冲突和人工标记交运营核查，禁止猜测成功、直接补票或强制释放。检测失败下轮重试，持续失败通过日志与运营手动查询发现；修复缺陷后以原业务编号重试既有协议并再次检测。

测试应证明正常生命周期和历史重售无误报、显式故障能检出且不修改数据、跨并发提交仍读同一快照、失败与回绕可恢复。实际实现/执行证据另记第六周周报。
