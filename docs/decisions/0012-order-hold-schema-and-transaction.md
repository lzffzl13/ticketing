# ADR-0012：订单快照、整组锁与当前占用在同一 MySQL 事务中提交

- 状态：已接受，2026-10-08 负责人确认首个闭环全部方案并授权实施
- 范围：Q-04 存储、V2 表结构、下单事务和模块边界

## 业务问题与选择

订单需要记录买了什么、多少钱；座位锁需要表达整组占用和期限；库存需要快速且唯一地回答当前由谁持有。只把这些信息放进一个状态字段会混淆职责，对历史锁明细的座位 ID 建永久唯一约束又会阻止释放后的重新购买。

采用 customer_order / order_item 保存订单和成交快照，seat_hold / seat_hold_item 保存锁组及历史关联，session_seat 的状态和 current_hold_id 保存当前占用。MySQL 为事实来源，不引入 Redis。一个库存行只有一个当前持有者，HELD 当且仅当持有者非空；复合外键保证订单、锁、座位及票档属于同一场次。金额、整组数量、ACTIVE 与共同期限由创建事务维护，外键不能单独证明这些跨表不变量。

V2 同时创建账号和令牌摘要表，身份决策见 ADR-0013；V1 不改写。请求与令牌的 SHA-256 摘要保存为 CHAR(64) 十六进制 ASCII 字符串，简化 MyBatis 映射；幂等键大小写精确匹配。

## 事务与模块决定

trade 的 OrderService 在写事务外规范化请求和查重；独立 OrderTransactionService 开启 READ COMMITTED，调用 catalog 服务取得场次行锁，锁内再查请求身份，读取最新销售资格与库存，取得 UTC 微秒 Clock 时间并校验完整 15 分钟边界。inventory 服务执行共用选座规则并整组占用；trade 写成交快照。所有订单、锁、明细与条件库存更新共同提交，任一步异常全部回滚。

catalog 和 inventory 的写服务使用 MANDATORY 加入调用者事务；跨模块通过服务，不访问别的模块 Mapper。不同场次相同消费者/键的请求由唯一键仲裁，失败写事务完全回滚后，OrderService 才在独立 REQUIRES_NEW 只读事务里重读已提交胜者并核对摘要。初查也走该查询入口，避免 NOT_SUPPORTED 外层同步绑定的 MyBatis SqlSession 缓存旧 null。锁等待或死锁映射可重试错误，客户端保留原键与内容。

个人订单查询使用独立只读 REPEATABLE READ，按认证消费者过滤后读取订单、锁及明细。写事务内的返回查询加入已有事务，不另开提交边界。

## 代价与验证

增加六张表及明确事务服务边界，换取可解释的职责、历史与原子性。同场次库存写入串行，暂不声称吞吐容量。OrderHoldIT 与 InventoryHoldFailureIT 验证竞争、唯一键仲裁、时间边界、部分写入及提交前失败；实际结果见第四周周报。到期后释放与支付恢复仍属于后续闭环，不以数据库时钟自动删除锁。
