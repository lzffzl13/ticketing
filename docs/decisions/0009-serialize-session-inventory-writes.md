# ADR-0009：场次行锁保护最终选座校验与整组库存写入

- 状态：已接受，项目负责人于 2026-10-08 明确确认并发建议
- 依据：[第四周首个闭环评审](../design/week-04-order-hold-review.md)第 2 节与本轮业务例子讲解
- 确认范围：场次行锁、取得锁后的最新状态重验、整组条件更新；完整首个闭环随后获批，结构与事务见 ADR-0012

## 业务问题与备选方案

同一段 1–5 全可售，甲买 1、2，乙买 4、5。各自按原布局检查都合法，两个请求的所选座位也没有交集，但共同提交后会留下新孤座 3。因此，只锁所选座位或仅对其执行 AVAILABLE 条件更新，不能保护孤座规则。

最终购买还要与运营人员暂停销售、停用票档形成明确先后顺序。现有管理写操作已先取得 session 行锁，见 ADR-0006。

| 方案 | 取舍 |
| --- | --- |
| 只对所选座位条件更新 | 能防止重叠占用，不能保护周围座位变化产生的孤座，也不能单独协调销售开关 |
| 完整相关分段锁及管理协调协议 | 可让不同段并行，但需要定义分段锁、多段顺序和管理协调规则，首版复杂度较高 |
| 场次行锁后重验，再整组条件更新 | 复用管理并发边界，容易解释和验证；接受同场次写事务串行的代价 |
| Redis 与 MySQL 组合 | 需额外解决邻座规则、销售开关和跨存储一致性；当前没有实测收益证据 |

## 已接受的决定

1. 同场次库存写路径在本地数据库事务内先取得 `session` 的 `FOR UPDATE` 行锁，再读取最新销售状态、启用票档和规则所需完整库存，执行选座规则及写入。
2. 手选不强制连座、推荐组合校验连座，两者都遵守最新购买资格和新孤座规则。规则与库存写入之间持续持有同一场次行锁。
3. 所选座位按稳定 ID 顺序执行带期望状态的条件更新，核对影响行数；任一不符或写入异常，整组事务回滚。
4. 后续取消、超时释放、退款回流等改变 AVAILABLE 集合的入口遵守同一场次锁协议。支付出票也协调场次、订单和持有者状态；外部支付调用不放在持有数据库锁的事务中。
5. 不同场次不使用一个全局 Java 锁。已有普通座位图和推荐继续采用只读一致性查询，不取得此写锁。

取得场次锁后的“最新读取”是已确认的并发要求；负责人随后接受 READ COMMITTED 写事务与完整提交范围，见 ADR-0012。不能因锁住 session 行就继续使用锁前已经建立的旧库存读视图。

## 两种锁的生命周期

数据库行锁在本地下单事务提交或回滚时释放。订单持有的业务座位锁则由持久化状态表达，普通期限为 15 分钟；到期后的安全释放继续遵守 ADR-0001。

甲的事务提交后，其他消费者可以继续购买本场次中符合规则的其他座位。并发保护不会让甲持有整个场次的数据库锁 15 分钟。

## 代价、验证与确认边界

- 同场次库存写事务串行，吞吐受事务耗时和锁等待影响。先建立正确性及实测基线，再决定是否细化锁粒度；没有锁座吞吐测试结果前不声称容量。
- 场次行锁是所有业务写入口遵守的协议，不会自动锁住子表或阻止直接绕过服务的 SQL。
- 最低验证包括重叠争抢、不重叠但影响孤座的争抢、下单与暂停/停用票档竞争、整组回滚及不同场次独立写入。
- 本轮新增真实 MySQL 并发与回滚测试；执行证据见第四周周报，122 项仍仅指原有回归基线。
- 首次确认仅覆盖并发建议；其后负责人接受幂等、时间以及剩余首个闭环方案，分别见 ADR-0010 至 0013。Q-04、Q-05、Q-11 均已解决。
