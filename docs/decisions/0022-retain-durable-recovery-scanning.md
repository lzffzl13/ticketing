# ADR-0022：首版保留 MySQL 持久恢复扫描，不引入消息或延迟组件

- 状态：已接受
- 日期：2026-10-21（Asia/Shanghai）
- 确认：负责人先选择“暂不定稿，先讨论替代方案”；讨论持久扫描、延迟消息及其故障边界后，明确回复“可以，你开始实行吧，现阶段采纳你的建议”。本次据此确认现阶段继续持久扫描，不引入 MQ 或延迟队列。
- 依据：[第七周方案比较](../design/week-07-reliability-review.md)、[ADR-0015](0015-local-payment-ticket-cancellation-recovery.md)、[ADR-0016](0016-scan-durable-payment-recovery.md)及[ADR-0018](0018-single-ticket-refunds-and-durable-recovery.md)。

## 业务问题与备选方案

支付截止只结束发起新支付的资格。已有支付可能已经成功、仍处理中或暂时无法查明；任务必须先确定原支付结果，成功则出票，确定未成功且安全关单后才释放。退款也必须恢复原请求和原通知，不能因处理超时就提前回流座位。

| 方案 | 收益及代价 |
| --- | --- |
| 当前应用内扫描 MySQL 持久计划 | 复用现有期限、恢复时间、租约及结果事务，无新增部署组件；应用停机时暂停，分批扫描可能排队 |
| 延迟消息触发原恢复服务，并保留 MySQL 兜底扫描 | 有机会减少轮询或改变唤醒时延；仍需幂等、锁内重验、可靠投递与确认、重投和兜底恢复，尚未实现或实测 |
| 仅按内存计时或过期通知直接释放 | 不能作为支付结果依据，也不能独立覆盖进程中断后的恢复，不符合当前安全释放规则 |

## 已接受的决定

1. 首版继续使用应用内 MySQL 支付与退款恢复扫描，不新增 MQ、延迟队列、Redis 过期通知或独立调度服务。
2. 支付与退款仍默认每轮结束后等待 1 秒，每批最多 50 个候选。固定最大 ID 上界，跨批前进和回绕；候选查询结束后逐笔恢复，整批无外层写事务。参数可配置，不作为时延或吞吐承诺。
3. MySQL 保存原业务编号、期限、下一恢复时间、错误、人工标志与领取信息。自动入口在业务锁内重验资格，复用 60 秒 token 租约；旧任务可幂等应用可信结果，但不能结算或清除新领取。
4. 正常未决状态继续复查；实际故障沿用 5 / 15 / 30 / 60 / 120 秒退避，连续 6 次或持续实际异常 10 分钟转人工。未知支付或退款继续占座，不强行猜测结果。
5. 渠道事实、本地结果和通知确认保持既有独立提交边界。支付复用原编号查单与安全关单；退款复用原编号补发及原通知重投，业务终态后仍可恢复尚未完成的通知确认。单笔失败隔离，查询失败下轮重试，重启从持久事实重新发现。

选择理由是当前恢复协议已有实现和故障证据，扫描可以复用这些事实，不必新增投递与消费协议。尚无扫描容量或唤醒时延测量证明增加消息组件的收益，也没有已确认的目标要求它。本决定不否定延迟消息可能带来的收益；消息仅能触发处理，不能替代查单、关单或本地原子事务。

## 已测与未测的边界

第五周已实际验证遗漏支付通知后的自动出票，以及渠道成功、本地未完成时更换真实应用进程后自动恢复支付和退款，见[第五周周报](../progress/week-05.md)。这些是历史重启证据，不写成本轮新执行。

第七周上一小闭环于 2026-10-21 10:42:59 +08 完成 426 项回归；新增提交后通知确认失败、旧任务失租接管与真实 SQL 回滚、双扫描器重试、取消重售后历史通知验证，见[可靠性报告](../testing/week-07-reliability.md)。这些通过受控 Clock、latch 和测试异常复现特定窗口，不是实际杀进程、数据库宕机或跨机网络丢包实验。接续的独立进程实验尚不能据此记为通过。

尚无扫描积压容量、端到端安全释放时延分布或延迟消息对照数据。第四周 100 / 500 座完整下单基线也不测这些指标。因此不能宣称“一秒内释放”“每秒处理 50 单”或“扫描优于消息系统”。

方案确认后，同日已补充[有限健康积压观测](../benchmarks/week-07-observations.md)与[真实进程终止后的原编号恢复](../development/week-07-restart-demo.md)。积压采用受控到期与紧凑服务调用，仍未建立生产积压容量、默认调度的端到端释放时延分布或消息对照；首轮重启受系统睡眠干扰的失败记录明确保留。

## 限制、检测与重评条件

- 应用停机期间不处理，重启后重新发现持久任务；大量候选、逐笔处理和同场次锁等待都会增加排队。进程内游标只影响访问顺序，不承担任务持久性。
- 活动租约和故障退避可能延迟恢复；达到人工阈值后自动尝试暂停。当前依赖日志、运营查询和既有手动恢复，没有外部告警或完整异常工单平台。
- 同场次只读一致性报告检查本地关系，报告无差异不等于渠道交易和通知全部结束；它不替代恢复，也不直接修表。
- 当前模拟渠道与本地业务共用 MySQL 实例但独立事务，尚未验证真实外部支付故障、数据库宕机或多 JVM 调度隔离。

后续先明确需要满足的恢复积压和时延目标，在固定数据规模、机器环境与并发模型下测量候选发现、任务领取、渠道处理、结果提交和积压清空。若扫描在合理调参及既有查询优化后仍达不到目标，或独立工作进程有明确收益，再评审延迟消息方案；同时说明数据库提交后未发消息、消费后未确认、重复迟到及消息组件停机如何检测、重试和恢复。替代方案须保留数据库事实与兜底机制，完成同条件对照并经负责人确认后实施。
