# ADR-0017：按需生成 HMAC 电子票凭证与本人票码查询

- 状态：已接受
- 日期：2026-10-15（Asia/Shanghai）
- 确认：负责人已阅读票码评审第 9 节，明确接受第 1、2、4 项，第 3 项也接受，并要求明确密钥保留期限及紧急撤销使旧码失效的机制。以下规则落实该要求，不新增业务范围。

## 业务问题与选择

原订单 O1、原支付 P1 已成功并签发 T1 后，查看二维码只为原票提供凭证，不重新支付或出票。票码需能拒绝篡改，始终绑定原票；T1 退票后即使原座位卖出并签发 T2，旧码也不能获得新票的资格。

比较独立随机凭证、HMAC 与公私钥签名后，选择 `TKT1.<kid>.<ticketNumber>.<mac>`，使用独立 32 字节随机秘密和 JDK HMAC-SHA256，覆盖前三段完整原文。严格限定版本、字段、长度及规范编码，不接受客户端指定算法或密钥来源。

收益是本人查询时可为既有票按需生成，重复查询不写库，不改 V4 及原支付出票事务。代价是管理全局密钥，无法单独撤销某一份泄露截图。完整静态码被复制后仍真实，正式核销依靠实时票状态与原子更新最多成功一次，不能保证原持有人先入场。

## 密钥保留期限：准确截止上界，不按固定天数

设 K1 停止签发的时刻为 S。在所有仍持有 K1 签发能力的本项目进程停止后，查询全部既有电子票关联场次：

```text
retainUntil(K1) = MAX(既有电子票所属场次.admission_close_at)
```

该查询不按票状态过滤，保守覆盖所有可能曾使用 K1 的票。已开售场次时间冻结；新票码在重启后使用 K2，因此不会扩大 K1 的旧票范围。记录 S、K1 及精确 UTC 上界。若没有任何票，可在完成轮换后立即移除 K1；查询失败或保留记录不明时禁止普通移除。

- `now < retainUntil(K1)`：K1 保留在受信集合中，仅用于验证，不能再签发。
- `now >= retainUntil(K1)`：所有可能使用 K1 的票均已到入场截止，可移除 K1，重启后不再验证 K1。半开入场窗口在相等时已经结束，无须额外加一天。
- 若重新启用 K1 签发，旧上界失效，必须重新停签、查询并延长保留记录；正常脚本不复用旧 kid，避免此操作。

例如停签时全部既有票最晚截止为 `2026-10-31T11:55:00Z`，即北京时间 10 月 31 日 19:55，K1 必须保留至该时刻。在此之前查询 T1 可生成 K2 新码，K1 原截图仍能验真；两份码都只对应 T1，不增加核销次数。

期限通过操作记录和退役脚本校验，首版不增加自动删除任务。到期后尚未执行移除时，K1 仍能完成密码学校验，但所有关联场次已截止，不能据此获得入场资格。此期限定义在线受信集合的兼容保留；受控恢复备份不会被自动物理销毁，已退役或撤销的秘密即使仍在备份中，也禁止恢复为受信项。

## 紧急撤销：从受信集合移除旧编号，停止旧进程并重启

紧急撤销不等待正常保留期限。停掉所有使用旧配置的本项目进程，生成独立 K2，将 K2 设为当前签发项，**从受信密钥集合移除 K1**，记录 K1 已撤销，再用新配置启动。

后端按二维码中的 kid 查受信密钥。旧码写的是 K1，而新集合中已无 K1，因此在验证入口直接拒绝为无效凭证；不会遍历其他密钥碰运气，不会退回接受裸票号，不会因为原票仍 VALID 就跳过验真。仅切换 activeKid、保留 K1 验证能力，不构成撤销。

**生效时刻是所有旧进程已停止，且对外服务的进程均已加载撤销后的受信集合之时。**只修改磁盘文件不使运行进程立即失效；首版无热加载或验真结果缓存。撤销后禁止回滚到重新信任 K1 的配置或备份，脚本元数据永久保留撤销编号，推荐的 run-app 启动预检拒绝重新引入。手工绕过脚本启动或同时回滚全部历史不在这种防回滚保障内，Java 本身校验的是指定密钥集合，详见运行导读。

消费者重新登录查询原票 T1，得到 K2 码。原订单、支付、票号及票状态不变；合法 K1 截图也必须重新获取。这里的“旧码失效”指在线系统不再信任该密钥，图片内容和原 HMAC 字节本身不会被远程改写。

## 查询、状态与阶段边界

- 本人原票记录查询保留历史状态；新增本人文本与 PNG 接口只为 VALID 且 `now < admission_close_at` 的票取码，开放前可提前获取。
- CONSUMER 角色、本人订单归属、票属于该订单均在后端检查；跨人/跨订单/不存在统一 404，错误角色 403，未登录 401；状态不符或已截止为 409。
- trade 负责归属与编排，读取票及场次窗口使用同一只读快照，结束事务后编码；ticketing 不反向访问 trade。响应 no-store，不在 URL 或日志保存完整票码。
- 密钥文件通过受控本地配置注入，启动时严格校验；缺失或非法不能随机补钥。测试密钥与开发密钥分离。ZXing 只编码二维码图片，不承担验真或入场判断。
- REFUNDING 暂停资格；退款失败恢复原票 VALID 时，受信原码可恢复使用；REFUNDED / CHECKED_IN 终态拒绝。查询快照不预授权未来核销。
- 第五周本闭环提供本人取码、内部严格验真、配置和演示。正式核销/审计及完整竞争仍在第六周；退款结构、模拟器、幂等与回流另行评审。

## 验证要求

实现评审稿 W5-Q01–Q10：二维码解码与原文一致、篡改/格式拒绝、本人查询权限矩阵、状态/时间边界、重复/并发只读、普通换钥兼容、撤销拒绝、重启读取原密钥以及生成失败不改变出票事实。使用数据库夹具验证后续状态时必须标明夹具，不称为退款或核销入口已完成。

实现、实际测试、真实应用演示和负责人理解验收分别记录于第五周周报；接受本 ADR 不代表这些验证已经完成。
