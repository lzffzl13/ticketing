# ADR-0016：应用内扫描持久的到期订单与支付恢复任务

- 状态：已接受
- 日期：2026-10-14（Asia/Shanghai）
- 确认：负责人对“应用内定时扫描 MySQL，默认每轮结束 1 秒后运行、每批最多 50 单，并复用已确认的安全取消与恢复协议”回复“采纳建议，实施这个闭环”。

## 背景与备选

第四周已有运营主动恢复，但停机中断或到期订单不能依赖人工逐单推进。到期只结束新支付资格，自动任务仍须查原支付、成功优先出票、安全关单后释放。

比较应用内数据库扫描、延迟消息/独立调度组件和继续仅人工处理。采用应用内 MySQL 扫描：已有恢复字段、索引与租约可以直接复用，不增加部署和消息投递补偿；代价是轮询延迟与应用停机期间不处理。方案及验收见[第五周首个闭环评审](../design/week-05-timeout-recovery-review.md)。

## 决策

- Spring 应用内定时触发，默认每轮结束 1 秒后再运行，每批最多 50 个候选，配置支持启停与调整参数。这些是开发运行默认值，不是性能承诺。
- MySQL 订单期限、恢复时间、人工标志和租约为持久事实，复用 PaymentService.recoverIfDue 与 ADR-0001 / 0015；不新增表、Redis、MQ 或分布式锁。
- 只读获取候选 ID 后结束查询事务，逐单恢复；整批无外层事务、渠道调用期间不持有本地订单或库存锁。
- 候选排除人工介入与活动租约；恢复时间非空时必须到重试时间，不能因为支付截止绕过故障退避；恢复时间为空时只处理已到期或已有取消意图的订单。
- 自动入口取得场次/订单锁后，在任何取消或释放副作用前重新核验上述资格。运营恢复可越过退避/人工标志，继续遵守活动租约。
- 每次完整遍历固定最大订单 ID 上界，跨批按 ID 前进，到尾回绕，新订单在下一次遍历纳入。游标只决定访问顺序；重启从头扫描，由幂等与租约避免额外业务结果。
- 一单异常不阻塞后续候选；候选查询失败记录批次错误并在下轮重试。领取后中断由现有 60 秒租约检测并接管，达到人工阈值暂停自动尝试。

## 验证与限制

普通集成测试禁用真实后台调度，使用可控 Clock 驱动单轮扫描；单独验证实际定时触发与配置关闭。覆盖到期、未决支付、查单/关单故障、候选过期、人工/退避/租约重验、重复、并发、批量公平性和中断恢复。

没有测量前不承诺释放时延或吞吐。应用停机期间座位可能继续被占用，重启重新发现；未知支付不能由任务强行释放。实现与执行证据单列在第五周周报，不以本 ADR 代替测试通过。
