# ADR-0021：首版保留 MySQL 场次行锁，不引入 Redis 预占

- 状态：已接受
- 日期：2026-10-21（Asia/Shanghai）
- 确认：负责人先选择“暂不定稿，先讨论替代方案”；讨论分段锁、Redis 预占及其边界后，明确回复“可以，你开始实行吧，现阶段采纳你的建议”。本次据此确认现阶段保留场次行锁，分段锁留作后续对照，不引入 Redis。
- 依据：[第七周方案比较](../design/week-07-reliability-review.md)、[第四周锁座基线](../benchmarks/order-holds-baseline.md)、[ADR-0009](0009-serialize-session-inventory-writes.md)及[ADR-0012](0012-order-hold-schema-and-transaction.md)。

## 业务问题与备选方案

锁座必须同时保护整组座位、最新销售资格和孤座规则。同场次的不同座位也可能互相影响：1–5 五座全可售时，甲买 1/2、乙买 4/5，各自按初始库存检查都合法，但共同提交会留下新孤座 3。仅对各自选中的座位执行 AVAILABLE 条件更新，不能满足完整规则。

| 方案 | 正确性前提与代价 |
| --- | --- |
| 当前 MySQL 场次行锁、锁后重验及整组条件更新 | 管理与库存写入遵守同一场次锁协议，容易明确先后顺序；同场次写事务串行 |
| 完整相关分段锁及管理协调协议 | 有机会使无关分段并行；必须覆盖孤座判断的完整分段、跨段固定锁顺序，以及销售配置和全部库存写入口，尚未实现 |
| Redis 整组预占后 MySQL 落单 | 还需处理邻座规则、销售开关、双存储状态与中断恢复；Redis 内原子操作不等于 MySQL 订单和库存已经共同提交，尚未实现 |

## 已接受的决定

1. 首版继续使用已实现的 MySQL 场次行锁方案；不增加 Redis 预占、缓存锁或另一套当前占用事实。
2. 沿用 READ COMMITTED 写事务，先取得场次行锁，再读取最新销售状态、票档和规则所需库存；按稳定座位 ID 执行带期望状态的条件更新，订单、锁、明细和全部座位同事务提交。
3. 销售管理、支付出票、取消释放和退款回流继续遵守既有加锁与事务协议。外部渠道调用仍在本地业务锁事务之外；推荐仍是只读候选，提交时重新校验。
4. 分段锁保留为后续对照方案。本次不实施新的锁粒度、数据库结构或模块边界，也不以“只锁所选行”替代完整分段协议。

选择依据是已实现协议能够保护当前业务规则，可靠性路径已有可复核证据，且增加组件或细化锁范围会引入额外协议成本。当前尚无替代实现的收益证据，也没有已经验证的业务容量目标要求更换方案；不能由此推导其他方案没有收益。

## 已测与未测的边界

第四周基线在 Windows 11、Core Ultra 5 336H、约 31.55 GiB 内存、Java 21.0.12.1、MySQL 8.4.11、Hikari 上限 5 的本机环境执行。100 / 500 座场次分别以并发 1 为串行对照，观测并发 4 / 8，共 104 个正式样本、26 次预热。计时覆盖完整下单服务调用及连接、锁等待和提交，不含 HTTP；请求购买同场次互不重叠的独立两座对。

该基线未分解锁等待占比，并发 8 超过连接池上限，有限样本及同机负载也未完全控制。因此不将完成速率写成生产容量，不认定场次锁是唯一瓶颈，不声称 Redis 或分段锁性能更优或更差。

## 限制与重评条件

- 同场次业务写入串行，完整布局重验、事务耗时和连接等待都会影响响应；不同场次使用不同数据库行锁，不使用全局 Java 锁。
- 场次锁依赖所有相关写入口遵守协议，不会自动阻止绕过服务的直接 SQL；数据库约束和一致性检测仍需保留。
- 尚未建立生产容量承诺，也未验证多 JVM 部署和数据库宕机恢复。并发正确性测试与本机基线不能填补这些证据。

若后续明确的并发规模和响应目标在可重复实验中不能满足，先测量连接等待、场次锁等待、规则计算和 SQL / 提交耗时，再决定优化对象。确需分段并行时，先评审完整分段与管理协调协议，覆盖孤座、跨段选择、释放、退款和配置竞争，再与现有方案在相同数据、环境和负载下对照。只有验证收益足以抵偿复杂度，并经负责人确认，才替换本决定；不为技术关键词新增组件。
